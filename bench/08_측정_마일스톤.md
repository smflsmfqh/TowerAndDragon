## 작업 원칙

- **실제 코드(`Assets/Scripts`)는 계측 전용 패치 외에 손대지 않는다.** 패치는 적용 전 diff를 저장하고, 끝나면 내가 넣은 부분만 역적용한다. 파일 전체 `checkout`/`reset`으로 되돌리지 않는다(§3-1).
- `Assets/Bench/`는 `.git/info/exclude`에 넣는다(`.gitignore` 수정 금지 — 공용 파일).
- 하네스 코드도 프로젝트 규칙을 따른다: UniTask(`WaitUntil`/`NextFrame`), `async void` 금지, `this.GetCancellationTokenOnDestroy()`. 문자열·리터럴 상수 규칙은 벤치 코드라 예외(CLAUDE.md 5항).
- 측정 프레임 안에서 문자열·로그·파일 쓰기를 하지 않는다. 숫자 버퍼에 담고 끝난 뒤 직렬화한다(§2-5).
- `Assets/TowerAndDragon_Imported`(별도 저장소)는 읽기만 한다.
- Coplay 생성형 기능 금지. `check_compile_errors`를 쓰면 루트에 생기는 .NET 리소스 덤프를 지운다.
- 이름이 같은 현재 API가 과거와 같은 일을 한다고 가정하지 않는다. M1의 대조표가 근거다(§1-3).

   `orthographicSize=5`, 위치 `(0, 1.8, -10)`에서 점령 후보 땅 셀 1,331개 중 **화면 안은 49개**뿐이고
   그 49개가 19개 행에 흩어져 있어 가장 긴 행이 6셀이다. 해상도를 올려도 같은 화면비라
   보이는 월드 범위는 그대로다.

   **B~D를 돌리기 전 넘어야 할 기준: 경로가 지나는 서로 다른 청크가 3개 이상**
   (`path_distinct_chunk_count`). 길이가 아니라 이 값이 기준인 이유는, T1은 해석된 **청크**가 바뀔 때만
   다시 그리고 S0는 매 프레임 다시 그리기 때문이다 — 한 청크 안에서만 움직이는 경로는 T1의 전환 비용을
   0으로 만들어 §2-3이 경고한 대로 비교를 T1에 유리하게 왜곡한다.
   확인 지표는 `marker_nonzero_frames["TND.Bench.T1.HoveredBorderRebuild"]`(실제 전환 횟수)다.

   카메라를 넓게 잡아 후보 지대를 프레이밍하고 pose를 기록한다(`camera_position`·`camera_orthographic_size`).
   **줌은 두 변형의 계산량 비교를 왜곡하지 않는다** — `RefreshCandidateBorders`·`RefreshTerrainTints`·
   `CacheAnnexableNeighbors`는 화면 보임과 무관하게 `_conquerableChunkBuffer` 전체를 돌고,
   S0도 청크 하나의 셀 전부를 칠한다. 늘어나는 것은 렌더링·배치 수이고 그건 두 변형에 똑같이 붙으며
   Batches/SetPass는 이미 별도 지표다. 대신 §5의 주장 범위에 "이 프레이밍에서의 값"이라고 한 줄 적는다.
2. **엔진 자동 샘플 `ConquestModeController.Update()`는 발화하지 않는다.** 리코더가 invalid일 뿐 아니라
   **raw에도 해당 샘플이 아예 없다**(호출 수 0). 리코더 미지원이 아니라 실제 미발화다 —
   Deep Profile 없이는 MonoBehaviour 단위 자동 샘플이 나오지 않는다. §2-3의 교차 확인을
   Deep Profile 별도 런으로 할지, "이 설정에서는 불가"로 적고 넘어갈지 M3에서 정한다.
3. **프레임 번호 대응.** 하네스의 `read_frame_count`(`Time.frameCount`)와 raw의 `frame_index`
   (프로파일러 로컬)는 기준이 다르다. 스모크 런에서 하네스 120프레임 ↔ raw 122프레임이었다.
   두 축을 잇는 오프셋 규칙을 확정하고 §2-2-1의 한 프레임 어긋남 검사를 그 위에서 한다.
4. **첫 측정 프레임의 처리 규칙.** 모든 런의 `frame_index 0`이 캡처 시작 비용을 안는다
   (스모크: 메인 스레드 548 ms, `batches`가 0 — 이후 프레임은 약 6,888). 제외할지 말지를
   **미리 선언**한다. 사전 선언된 제외는 런 선별이 아니지만, 사후 제외는 선별이다.
5. **디스크.** `.raw`가 S0는 약 0.22 MB/프레임, E는 약 1.6 MB/프레임이었다(3런 합계 593 MB).
   변형·시나리오에 따라 7배쯤 벌어지므로 **총합이 아니라 프레임당 값으로** 1,800프레임 × 44런을 잡으면
   런당 0.4~2.9 GB, 전체로는 수십~수백 GB가 될 수 있다. 파일럿에서 실제 런당 크기를 먼저 재고,
   보관 위치·압축 규칙을 M4 시작 전에 정한다.
   **"용량 때문에 불리한 런을 지운다"는 선택지는 없다**(§2-4) — 규칙을 미리 정한다.
6. **E-출발 버튼 경로 결정.** 스모크에서 **가상 마우스 실제 클릭이 EventSystem을 거쳐 동작함을 확인했다**
   (`e_button_mode: virtual mouse real click`, 전이 프레임 30 → `ConquerUI` 발화 39).
   `Button.onClick.Invoke()` 경로는 코드만 있고 실행된 적이 없다. §2-1 E가 요구하는 "하나로 고정하고
   이유를 기록"은 실제 클릭 쪽으로 기우는 근거가 이미 있으니, M3에서 확정만 하고 M5는 다시 따지지 않는다.
7. 그 밖에 M3 본문의 1~12 항목을 그대로 수행한다. 스모크에서 통과한 항목도 정식 파일럿에서 다시 잰다.

### 측정 전 환경 조건 (스모크 런에서 실제로 막혔던 것)

1. **콘솔의 Error Pause를 끈다.** 씬 로드마다 `ExpeditionMarkerRenderer.OnEnable`에서
   NullReferenceException이 난다(이번 측정과 무관한 기존 문제). Error Pause가 켜져 있으면 그 예외에
   플레이 모드가 일시정지되어 프레임이 멈추고 복원이 끝나지 않는다.
   증상: `Time.frameCount`는 고정인데 `realtimeSinceStartup`만 올라간다.
2. **Unity 에디터 창을 앞에 둔다.** 비포커스에서는 플레이 루프가 돌지 않는다
   (`Application.runInBackground = true`로도 풀리지 않았다). 스모크 런의 프레임 시간이
   약 100 ms였던 것도 이 영향이며, **이 수치는 성능 결과가 아니다.**
3. **Game 뷰 1920×1080 · Scene 뷰 비활성**(§2-5).
4. 런 하나마다 플레이를 껐다 켠다. 도메인 리로드 없이 연달아 돌면 `BenchSession.Reset()`이
   받아 주지만, 설정은 런처에서 매번 다시 지정한다(`IsEnabled`는 진입 때 소비된다).

## M3 — 파일럿

**S0·T1 각각 시나리오 A와 D를 1런씩, E-출발·E-재진입도 각각 파일럿을 수행한다.** 결과는 본 측정에서 제외한다(§2-4). 목적은 관문 통과 여부와 오버헤드 숫자를 얻는 것이다.

선행: M2.

작업 (각 항목의 결과를 아래 「파일럿 결론」에 숫자로 적는다):

1. **입력 대응** — 의도 셀 vs `GetHoveredCell()` 시퀀스 100% 일치(§2-2-1). 한 프레임 어긋남이 있으면 하네스의 프레임 번호 대응을 고친다. 허용 비율로 넘기지 않는다.
2. **S0 풀** — `_selectionHighlightRenderer` 참조 획득 성공, 기본 하이라이트 스프라이트인지(안내 스프라이트면 실패 처리), 벤치 루트 아래 seed의 월드 스케일·정렬·머티리얼이 원본과 같은지 스크린샷 대조.
3. **두 구현 격리** — S0 실행 중 T1의 경계선·틴트가 없고, T1 실행 중 S0 풀이 비활성인지.
4. **마커** — 명시적 호버 마커 리코더 `Valid`, 엔진 자동 샘플 `ConquestModeController.Update()` 리코더 `Valid`. 패치 있음/없음 두 상태로 A를 돌려 **명시적 마커 오버헤드를 실측**한다(§2-3). 결과가 T1 정지 프레임 값과 같은 자릿수면 "정지 시간은 계측 한계 이하"로 표기하기로 하고 배율을 내지 않는다.
5. **raw** — Frame Count 2,000 설정 → `.raw`에 1,800 + 여유 프레임이 전부 있는지, `ProfilerDriver.LoadProfile` 후 로드 프레임 범위가 하네스 메타와 일치하는지.
6. **CSV ↔ raw** — 마커 합 ±5%, 작은 값은 절대 오차(파일럿에서 정한다) 안인지.
7. **카메라·입력 불변** — 시작/끝 pose 동일, 전 프레임 `Mouse.current == 가상 마우스`.
8. **하네스 오버헤드** — 하네스만 켜고 변형 없이 A를 돌린 프레임 CPU·GC와, 하네스 없이 정지한 프레임의 값을 비교해 기록.
9. **ChunkDebugger 등 배경 렌더러** 비활성 확인. 배치 수가 두 변형에서 같은 배경값에서 출발하는지.
10. **런당 소요 시간 실측** — 진입·복원·워밍업·측정·저장 각각. 이 값으로 M4·M5 예상치를 아래에 적는다.

11. **E 준비 검증** — 정상 완료 상태와 디버그 완료 준비 상태의 일치, 버튼 실행 방식, 비동기 안정 조건, E 마커를 검증한다. 정상 정산의 성능 측정은 M7 선택이지만 상태 동등성 확인은 M5 전에 필수다.
12. **짧은 기능 검증** — 같은 좌표의 상태 변경, 빈 영역 표시 제거, 구멍·분리 영역·대각선 경계를 확인한다. 카메라 위치·회전·줌은 시작/끝뿐 아니라 측정 중 불변을 확인한다.

### 파일럿에서 찾아 고친 것 (2차까지 돌았다)

파일럿 1차 산출물은 `superseded/`에 `pilot_iter1_*`로 보존했다(§2-4).

1. **경로에 겨냥할 수 없는 셀이 섞여 있었다.** 셀 `(-7,-18)`은 더 높은 이웃 타일 `(-8,-19)`이 중심점을
   덮고 있어 그 화면 좌표를 주입하면 항상 `(-8,-19)`가 읽힌다. D 시나리오의 입력 대응이 깨졌다
   (S0_D 74/1800 불일치). → 경로를 만들 때 셀마다 **화면 좌표 → 셀 왕복**을 확인해 자기 자신이
   나오지 않는 셀을 뺀다. 이번 스냅샷·pose에서 11개가 빠졌다.
2. **입력 대응 불일치가 유효성 판정에 반영되지 않았다.** 74/1800이 어긋난 런이 `is_valid=true`로

### ⚠️ `recorder_valid`는 "수집됐다"의 근거가 아니다

### E-출발 버튼 경로 결정 (§2-1 E가 요구하는 "하나로 고정")

**가상 마우스로 실제 클릭한다**(`BenchConfig.EUsesRealClick = true`). `Button.onClick.Invoke()`는 쓰지 않는다.

이유: 실제 클릭 경로는 M3에서 동작이 확인됐다 — 청크 선택 → 패널 열림 → 버튼 위로 커서 이동 →
누름 → 뗌이 EventSystem을 거쳐 `OnConquerButtonClicked`까지 도달했고(`ConquerUI` 마커 1회 발화),
패널 열림·버튼 활성·버튼 화면 좌표가 결과에 기록된다. `onClick.Invoke()` 경로는 코드만 있고
한 번도 실행된 적이 없어 근거가 없다. 매니저 직접 호출은 §2-1 E가 금지한다.

클릭은 한 프레임에 끝나지 않는다: 전이 프레임에 패널을 열고, +4프레임에 누르고, +4프레임에 뗀다.
입력 이벤트가 큐를 거치므로 마커는 전이 프레임 +9에 발화한다.

- 정산 시점엔 모드가 꺼져 있고 패널 구독도 해제돼 있다. "완료 순간의 하이라이트 갱신"은 **존재하지 않는다** — 재진입 갱신만 잰다(§2-1 E). 이걸 "완료 이벤트 비용"으로 부르지 않는다.

#### 구간별 GC — 전체 프레임 GC로 대신 말할 수 없다

`HierarchyFrameDataView`의 `columnGcMemory`로 구간별 할당을 뽑았다.

- **호출 1회당으로는 T1이 더 많이 할당한다** — 같은 시나리오끼리 비교하면

불일치가 **0건**이다. 시간값의 오차 기준과 무관한, 대응 자체에 대한 직접 근거다.
오프셋도 54런 전부 **+0**이며, 1만 밀면 중앙 절대차가 166 ns → 63,792 ns로 380배 커진다.

시간값은 두 출처의 고정 차이를 갖는다 — 비교 쌍 91,057개에서 하네스−raw가
양수 99.58% · 음수 0.00%, 중앙 +126 ns. 읽는 경로가 다르기 때문이다
(하네스는 `ProfilerRecorder.LastValue`, raw는 저장된 샘플).
이 치우침은 대응이 맞다는 것과 모순되지 않지만 **그 자체로 대응을 증명하지는 않는다.**

판정선으로 **상대 ≤5% 또는 절대 ≤5,000 ns**를 썼고 **91,057쌍 중 초과 1건**이다
(`T1_D_run1` f31, 하네스 73,375 ns ↔ raw 56,250 ns — 원인 미규명, 그 런의 raw는 이미 지웠다).
⚠️ **이 절대값은 같은 자료의 차이 분포를 보고 정한 탐색적 기준이며 사전 기준이 아니다.**
§2-4가 요구한 사전 정의 절대 오차는 M3에서 두지 못했고 그 공백을 사후에 메운 것이므로,
이 선을 통과했다는 사실만으로 정확도를 주장하지 않는다.

#### 정상 정산 ↔ 디버그 완료 — 점령 상태 완전 일치

같은 스냅샷에 대해 서로 다른 세션에서 두 경로를 돌려 상태를 덤프하고 `diff`했다.
디버그는 `DebugForceCompleteAllExpeditions()` 1회, 정상은 `ForceEndDay()`+`EndNight()` 2주기로
`OnNightEnd`의 `OnSettlement`을 실제로 통과시켰다. **`## AFTER` 구간에 차이가 없다** —
점령 청크·공개 청크·분류·편입·활성 원정·적 강화가 모두 같다.
두 경로가 같은 `CompleteConquest()`를 부르고 차이는 일수 진행·완료 판정뿐이라는 코드 구조와도 맞는다.

한계: 밤 전투를 치르지 않아 자원·인구·적 상태·일차는 다르다. 이 검증은 **점령 관련 상태에 한정**하며
게임 전체 정산과 동등하다는 주장이 아니다. 원정이 2개 이상인 스냅샷에서는 확인하지 않았다.
