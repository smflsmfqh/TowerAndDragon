## 3. 읽어낸 것

### 3-1. 비용의 주범은 관리 코드가 아니라 `Tilemap.SetColor`

전체 재계산 1회를 구간으로 쪼개면:

| 구간 | 1회 | 셀당 | 비중 |
|---|---:|---:|---:|
| 틴트 수집 (딕셔너리 채우기) | 0.456 ms | 0.097 µs | 약 20~40% |
| **타일맵 반영 (`SetColor`)** | **1.788 ms** | **0.380 µs** | **약 60~80%** |

> 비중에 폭이 있는 이유는 4-2다. 두 구간을 따로 재어 더한 값(2.244 ms)과 합친 채로 잰
> 값(1.209 ms)이 어긋나기 때문이다. 앞을 기준으로 하면 80%, 뒤를 기준으로 해도 62%로
> **어느 쪽이든 `SetColor`가 지배적**이라 결론은 바뀌지 않는다.

**"알고리즘을 최적화한다"로 갈 수 있는 여지가 많아야 그만큼뿐이라는 뜻이다.** 수집 루프를 공짜로
만들어도 1.788 ms가 남는다. 반대로 호출 횟수를 줄이면 2.24 ms 전체가 사라진다.

`06_ 4-3`의 "계산을 더 빠르게가 아니라 필요 없는 계산을 없앰"이라는 선택은 감이 아니라
이 숫자에서 나왔다. 개선 방향을 정하기 전에 이 구간 분해를 먼저 했다는 게 이 측정의 요점이다.

### 3-2. 셀 스프라이트 방식은 셀당 가장 비싸다

| 방식 | 셀당 비용 |
|---|---:|
| 개선 전 — 셀마다 스프라이트 (`SetActive` + 좌표 변환 + `transform.position` + `color`) | **0.70 µs** |
| 출시본 — 지형 타일 틴트 (`SetColor` 1회) | 0.38 µs |
| 출시본 — 틴트 수집만 (관리 코드) | 0.097 µs |

셀당 1.8배 차이다. `06_ 3-1`에서 "호버 청크가 바뀐 프레임에서도 출시본이 더 싸다"(②가
뒤집히지 않은 것)의 원인이 여기 있다 — 출시본은 **덜 자주 계산할 뿐 아니라 셀당 단가도 더 싸다.**
경계 변 수집과 폐곡선 추적을 얹고도 이길 수 있었던 이유다.

### 3-3. 프레임당 가비지는 데이터 크기가 아니라 할당기 블록으로 결정된다

113셀(데이터 1,356 B)과 163셀(데이터 1,956 B)이 **둘 다 약 1,965 B**로 나온다.
두 실행에서 1 B 차이로 재현되므로 노이즈가 아니라 **같은 할당 크기 구간에 떨어진 것**이다.
75셀도 데이터 900 B 대비 1,272 B가 나온다.

그래서 이 수치는 "리스트에 담긴 데이터의 크기"가 아니라 **"프레임마다 힙에서 실제로
버려지는 양"**으로 읽어야 한다. 후자가 GC를 부르는 값이므로 이쪽이 맞는 관점이다.

A/B 벤치마크가 독립적으로 잰 값(1,824 / 1,996 B)과 같은 자릿수다 — 두 측정이 서로를 뒷받침한다.
`06_`이 채택한 "프레임당 약 1.9 KB · 초당 약 115 KB"는 이 값에서 나왔다.

### 3-4. 이벤트 기반으로 바꾸면 재계산이 몇 번으로 줄어드는가

셀 10.4칸당 1회. 커서가 셀 경계를 넘는다고 매번 청크가 바뀌는 게 아니라,
**평균 10칸을 지나야 한 번 바뀐다.** `06_ 3-2`의 60초 세션 표(초당 40칸 → 3,600프레임 중
267회)는 이 비율에서 예측되는 값과 맞는다 —
`60초 × 40칸/초 ÷ 10.4 ≈ 231회`, 실측 267회. 궤적이 짧아(81칸) 끝에서 되감기며
경계를 더 자주 넘는 것을 감안하면 일치한다.

즉 **두 벤치마크가 서로 다른 방식으로 같은 결론에 도달했다.**

## 4. 계측 함정 — 이 로그를 다시 볼 사람을 위해

### 4-1. `관리힙 증가 0 B/회`는 아티팩트다

`Benchmark_SingleChunkHighlightRebuild`이 쓰는
`GC.GetAllocatedBytesForCurrentThread()`가 **이 Mono 런타임에서 구현돼 있지 않아 항상 0을
돌려준다.** 개선 전 경로는 실제로 호출마다 1.3~2.0 KB를 할당한다(2-3 표).

이 0을 "할당이 없다"로 읽으면 **결론이 정확히 반대로 뒤집힌다.** 그래서 가비지는
`Measure_PerFrameGarbageOfCoordList`에서 객체를 살려 둔 채 `GC.GetTotalMemory(true)`
차이로 따로 잰다. 로그를 인용할 때 이 행의 뒷부분은 잘라낼 것.

### 4-2. `SetColor` 곡선이 단독 측정보다 싸게 나온다 — 미확인 가설

숫자가 뒤집혀 있다.

| 측정 | 4,705셀 1회 | 하는 일 |
|---|---:|---|
| `Benchmark_RecomputeCostByChunkCount` (n=41) | **1.209 ms** | 딕셔너리 4,705회 삽입 + 순회 + `SetColor` 4,705회 |
| `Benchmark_TilemapSetColorForAllCells` | **1.788 ms** | `SetColor` 4,705회 **만** |

**일을 더 많이 하는 쪽이 더 싸다.** 두 실행 모두에서 같은 방향이라 노이즈가 아니다.

두 코드의 유일한 차이는 색이다 — 단독 측정은 반복마다 노랑/흰색을 **번갈아** 쓰고,
곡선 측정은 매번 **같은 노랑**을 다시 쓴다. `Tilemap.SetColor`가 색이 바뀌지 않으면
싸게 끝나는 경로를 탄다면 설명이 된다.

**이것은 Unity 내부 동작에 대한 추측이고 저장소 안의 어떤 것으로도 확인할 수 없다.**
확인 방법은 한 줄이다 — `Benchmark_RecomputeCostByChunkCount`의 `RunOnce()`에서
`Color.yellow`를 `(i % 2 == 0) ? Color.yellow : Color.white`로 바꿔 41청크 값이
1.788 ms 쪽으로 올라가는지 본다. 올라가면 가설이 맞고, **2-2의 곡선 전체는 하한**이 된다.

관련해서, 곡선 측정(1.209 ms)과 A/B의 ⑤(0.921 ms)가 다른 것은 **별개 문제**다.
둘 다 색을 고정해 쓰므로 조건이 같고, 차이는 그냥 실행 간 편차다.

### 4-3. 편차는 항목마다 다르다 — 특히 전체 스캔

| 측정 | 1차 → 2차 | 편차 |
|---|---|---:|
| **전체 청크 분류·틴트 수집** | 0.2859 → 0.4556 ms | **+59%** |
| 하이라이트 재구성(중앙값) | 0.0678 → 0.0788 ms | +16% |
| 지형 틴트 재도색 | 2.144 → 1.788 ms | −17% |
| 좌표 리스트 크기 | 1,969 → 1,965 B | +0.2% |
| 청크 변경 빈도 | 453 → 453회 | 0% |

`README.md`가 말하는 "실행 간 편차 20%"는 평균적인 이야기고, **전체 스캔만 유독 크다.**
이 항목의 절대값은 인용하지 말고 "구간 비중이 20% 정도"라는 정성적 결론까지만 쓸 것.

그리고 `06_`과 달리 **이 초기 측정본은 보수적 값 채택 과정을 거치지 않았다.**
2회 실행 중 어느 쪽을 쓸지 정해 두지 않았으므로, 위 표의 값을 외부에 인용하려면
`06_ 3-0`처럼 불리한 쪽을 고르는 절차를 한 번 거칠 것.

### 4-4. 공통 한계 (두 벤치마크 모두)

- **EditMode `-batchmode -nographics` 기준값이다.** 실제 빌드 플레이 모드보다 오버헤드가 크다.
  상대 비교는 유효하지만 절대값을 "게임에서 이만큼 걸린다"로 옮기면 안 된다.
- **렌더링(드로우 콜·배칭)은 포함하지 않는다.** 관리 코드와 Unity API 호출 비용만 잰다.
- **청크의 전체 셀을 대상으로 잰다.** 출시본은 실제로 `LandCellCoords`(육지 셀)만 칠하므로
  출시본 쪽 비용이 실제보다 다소 크게 나온다 — 개선 폭을 부풀리지 않는 방향의 오차다.
- **41청크는 상한이다.** 실제 판정 대상은 그 시점 `ChunkState.Visible`인 청크뿐이고,
  `Conquered`·`Hidden`은 루프에서 걸러진다.

## 6. 재현

두 벤치마크 파일 모두 `Assets/` 안에 없다 — 제출본을 깨끗이 두려고 측정 후 지웠다.

```bash
cp bench/ConquestHighlightBenchmark.cs \
   ~/unityProject/TowerAndDragon/Assets/Tests/Editor/

/Applications/Unity/Hub/Editor/6000.3.15f1/Unity.app/Contents/MacOS/Unity \
  -batchmode -nographics \
  -projectPath ~/unityProject/TowerAndDragon \
  -runTests -testPlatform EditMode \
  -testFilter "ConquestHighlightBenchmark" \
  -testResults /tmp/bench-results.xml \
  -logFile /tmp/bench.log

grep "\[BENCH\]" /tmp/bench.log

# 측정이 끝나면 저장소를 되돌린다
rm ~/unityProject/TowerAndDragon/Assets/Tests/Editor/ConquestHighlightBenchmark.cs*
git -C ~/unityProject/TowerAndDragon status --porcelain   # 비어 있어야 한다
```

Unity 에디터가 **같은 프로젝트**를 열고 있으면 배치모드 실행이 막힌다.
다른 프로젝트가 열려 있는 것은 상관없다.

**측정 환경**: Unity 6000.3.15f1 · `-batchmode -nographics` · Apple Silicon Mac (Darwin 24.6.0)
