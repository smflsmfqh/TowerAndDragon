# 점령 하이라이트 최적화 — 결과 분석 (포트폴리오 작성용)

작성 2026-10-02 · 근거: [`09_측정결과.md`](./09_측정결과.md)(결과 문서) · 남은 한계 원문: [`11_보완작업_마일스톤.md`](./11_보완작업_마일스톤.md) 「마무리 상태」

이 문서는 측정 결과를 **포트폴리오 문장으로 옮기기 위한 해설**이다. 새 측정은 없다.
수치마다 ① 한 줄 요약 ② 숫자 ③ 왜 그런가 ④ 쓸 때 붙일 단서 ⑤ 쓰면 안 되는 표현을 붙였다.
"계산" 표시가 있는 값은 결과 문서의 값을 이 문서에서 나누거나 곱한 것이며, 식을 함께 적었다.

---

## 0. 무엇을 비교했나 (모든 수치의 전제)

| | S0 — 과거 구현 경로 | T1 — 현재 구현 |
|---|---|---|
| 출처 | 커밋 `038b253e`의 하이라이트 처리 경로를 현재 프로젝트에 **이식** | 커밋 `061cc138`의 실제 코드 |
| 그리는 방식 | 커서 아래 청크의 **모든 셀**에 스프라이트를 깐다 | 청크 덩어리의 **외곽선**만 그린다 |
| 언제 다시 그리나 | **매 프레임** (변경 가드 없음) | 커서가 가리키는 청크가 **바뀔 때만** |

- 같은 맵·같은 세이브 상태·같은 가상 마우스 입력을 두 구현에 똑같이 넣었다.
- 입력 시나리오(측정 창 1,800프레임 = 가상 입력의 기준 시간으로 60fps 30초 분량. 실제 경과 시간이 아니다 — 에디터 프레임이 느려 본 측정 A\~D의 실제 측정 경과는 런당 약 77\~86초였다):
  **A** 커서 정지 · **B** 초당 5셀 이동 · **C** 초당 15셀 · **D** 초당 40셀.
- 환경: Unity 6 **에디터 플레이모드**, MacBook Air(M1), 고정 카메라. 본 측정은 칸마다 3회 반복.
- T1은 "변경 가드"와 "외곽선 표시" 두 가지가 함께 바뀐 결과다. **둘 중 무엇이 얼마나 기여했는지는 분리하지 않았다.**

> 포트폴리오 한 줄 전제 예: "과거 하이라이트 경로를 현재 프로젝트에 이식해, 같은 맵·같은 입력으로 현재 구현과 Unity 에디터 플레이모드에서 Profiler로 비교했다."

## 1. 한눈에 보는 결론

1. **다시 그리는 횟수**: 같은 1,800프레임(30초 분량)의 가상 입력에서 **1,800회 → 0\~76회**로 줄었다.
2. **하이라이트 처리에 쓴 시간**: 같은 1,800프레임에서 누적 **약 1.35\~1.45초 → 0.036\~0.073초**, 19\~38배 줄었다(시나리오별 3런 중앙값의 비).
3. **한계**: 이 처리는 S0에서도 프레임 시간의 약 1.7\~1.8%였고, **전체 프레임 시간에서는 런 간 변동과 구별되는 일관된 향상을 확인하지 못했다.**
   개선을 확인한 것은 "해당 처리 구간의 비용"이고, 게임 전체 속도가 아니다.

## 2. 수치별 분석

### 2-1. 다시 그리는 횟수 — 핵심 개선

**한 줄**: 커서가 멈춰 있어도 매 프레임 다시 그리던 것을, 가리키는 청크가 바뀔 때만 그리게 해서 재구성 횟수가 1,800회에서 0\~76회로 줄었다.

| 시나리오 | S0 | T1 | 계산: 감소율 = (1 − T1 ÷ S0) × 100% |
|---|---:|---:|---:|
| A 정지 | 1,800 | **0** | 100% |
| B 초당 5셀 | 1,800 | **11** | 99.4% |
| C 초당 15셀 | 1,800 | **29** | 98.4% |
| D 초당 40셀 | 1,800 | **76** | 95.8% |

- **왜**: S0는 변경 여부를 확인하지 않고 매 프레임 다시 그린다. T1은 커서가 가리키는 청크가 직전과 같으면 그리지 않는다.
  커서를 빨리 움직일수록 청크를 자주 넘나들어 T1의 횟수가 늘어난다.
- **믿을 수 있는 이유**: 3회 반복(보완 런 포함 4회)에서 **한 번도 값이 흔들리지 않았다**(전 칸 최소=최대). 입력은 프레임 단위로 같게 재생했다.
- **쓸 때 붙일 단서**: "30초 분량(1,800프레임) 가상 입력 기준". 실제 플레이어 입력의 빈도는 측정하지 않았다.
- **쓰면 안 됨**: "재구성을 없앴다"(이동하면 여전히 그린다), "모든 상황에서 95% 이상 감소"(시나리오 4개에서의 값이다).
- 근거: 09 §4 「실제 재구성 횟수」, `summary/summarize_output_main.md` 「본편」.

### 2-2. 하이라이트 처리에 쓴 누적 시간 — 체감되는 개선 폭

**한 줄**: 같은 1,800프레임(30초 분량)의 가상 입력에서 하이라이트 처리에 쓴 누적 시간이 약 1.35\~1.45초에서 0.036\~0.073초로, 19\~38배 줄었다.

| 시나리오 | S0 누적 | T1 누적 | 배율 (S0÷T1) | 계산: 프레임당 평균 S0 → T1 |
|---|---:|---:|---:|---|
| A 정지 | 1,348.6 ms | 35.9 ms | **37.6배** | 0.75 ms → 0.020 ms |
| B 초당 5셀 | 1,453.8 ms | 48.7 ms | **29.9배** | 0.81 ms → 0.027 ms |
| C 초당 15셀 | 1,446.1 ms | 55.1 ms | **26.3배** | 0.80 ms → 0.031 ms |
| D 초당 40셀 | 1,420.1 ms | 73.3 ms | **19.4배** | 0.79 ms → 0.041 ms |

(누적은 3회 반복의 중앙값. 프레임당 평균 = 누적 ÷ 1,800프레임.)

- **왜**: 2-1의 횟수 감소가 대부분이다. 다시 그리는 1회의 비용도 T1이 절반쯤이지만(2-3), 차이의 대부분은 횟수에서 온다.
- **입력이 빠를수록 배율이 준다**: T1의 다시 그리는 횟수가 늘기 때문이다. S0는 원래 항상 최대 작업을 한다.
  포트폴리오에는 **범위(19\~38배)로 쓰고, 가장 큰 값(37.6배)만 따로 쓰지 않는다.**
- **반복 수를 늘려도 같다**: 보완 런까지 4회로 내면 36.2 / 29.2 / 25.5 / 19.8배.
- **쓸 때 붙일 단서**: "해당 처리 구간(Profiler 마커로 잰 호버 처리)의 시간", "에디터 플레이모드".
- **쓰면 안 됨**: "게임이 38배 빨라졌다", "프레임 시간이 줄었다", "FPS가 올랐다" → 2-6 참고.
- 근거: 09 §4 표·「배율은 뒤에 쓴다」, `summarize_output_main.md`·`_all.md`.

### 2-3. 한 번 다시 그릴 때의 비용 — 부수적 개선

**한 줄**: 실제로 다시 그리는 프레임 하나의 비용도 약 0.7 ms에서 0.33\~0.37 ms로 절반 수준이다.

| 시나리오 | S0 (p50 / p95) | T1 (p50 / p95) | 계산: T1÷S0 (p50) |
|---|---|---|---:|
| B | 713.4 / 1,144.7 µs | 334.1 / 582.0 µs | 0.47 |
| C | 705.8 / 1,134.8 µs | 371.6 / 620.5 µs | 0.53 |
| D | 685.2 / 1,150.4 µs | 360.1 / 585.1 µs | 0.53 |

- **왜**: S0는 청크의 모든 셀에 스프라이트를 배치하고, T1은 외곽선만 다시 만든다. **두 작업은 같은 일이 아니다.**
  그래서 "같은 작업을 2배 빠르게 했다"가 아니라 "표시 방식을 바꿔 한 번의 작업량이 줄었다"로 읽는다.
- **쓸 때 붙일 단서**: p50은 중앙값과 비슷한 값(짝수 표본에서 가운데 두 값 중 윗값). T1/D p95는 분위수 계산 방식에 따라 585.1 ↔ 539.7 µs로 약 8% 달라진다(런당 표본 76개).
- **쓰면 안 됨**: 이 값을 "개선의 주원인"으로 쓰는 것. 주원인은 횟수다(2-1).
- 근거: 09 §4 표 각주 ¹.

### 2-4. 아무것도 바뀌지 않은 프레임의 비용

**한 줄**: 커서가 같은 청크에 머무는 프레임에서 S0는 약 0.7 ms를 쓰고, T1은 약 0.02 ms(20 µs)로 확인만 하고 끝낸다.

| 시나리오 | S0 (매 프레임 재구성) p50 | T1 재구성 없는 프레임 p50 |
|---|---:|---:|
| A | 686.5 µs | 19.1 µs |
| B | 752.8 µs | 21.7 µs |
| C | 746.2 µs | 21.5 µs |
| D | 705.2 µs | 21.6 µs |

- **왜**: T1은 "직전과 같은 청크인가"만 판정하고 반환한다.
- **쓸 때 붙일 단서**: T1의 19\~22 µs에는 **계측 마커·하네스 자체의 비용이 섞여 있을 수 있고, 그 크기를 분리하지 못했다.** "실제 비용이 20 µs"로 쓰지 않고 "계측값"으로 쓴다.
  또 S0 열은 커서 이동 여부와 무관한 "매 프레임 재구성" 표본이라, 엄밀한 1:1 비교가 아니다.
- **쓰면 안 됨**: "T1은 비용이 0이다", "35배 빠르다"(이 표로 배율을 만들지 않았다).
- 근거: 09 §4 「재구성 발생 프레임과 미발생 프레임」, `summary/transition_vs_still.md`.

### 2-5. 메모리 할당(GC) — 총량은 줄었고, 1회당은 오히려 늘었다

**한 줄**: 같은 1,800프레임에서 하이라이트 처리 구간의 메모리 할당 총량은 약 2.2\~2.8 MB에서 0\~0.6 MB로 줄었다(시나리오별 각 1런). 다만 한 번 다시 그릴 때의 할당은 T1이 약 5배 많다.

| 시나리오 | S0 총량 | T1 총량 | S0 1회당 | T1 1회당 |
|---|---:|---:|---:|---:|
| A | 2,188,800 B (2.19 MB) | **0 B** | 1,216 B | — (재구성 0회) |
| B | 2,793,168 B | 89,032 B | 1,552 B | 8,094 B |
| C | 2,803,536 B | 230,800 B | 1,558 B | 7,959 B |
| D | 2,792,760 B (2.79 MB) | 598,576 B (0.60 MB) | 1,552 B | 7,876 B |

- **계산**: "약 5배" = B\~D 같은 시나리오끼리 T1 1회당 ÷ S0 1회당 = 약 5.08\~5.22배. 표의 회당 값은 정수로 반올림한 것이고, 배율은 반올림 전 값(구간 GC ÷ 호출 수)으로 계산했다. 표의 정수끼리 나누면 D가 5.07로 나온다.
- **왜**: S0는 매 프레임 조금씩(약 1.2\~1.6 KB) 할당하고, T1은 다시 그릴 때만 더 크게(약 8 KB) 할당한다. 횟수 차이(1,800 ↔ 0\~76)가 1회당 차이를 압도한다.
- **쓸 때 붙일 단서**:
  - **칸마다 1회 측정이다.** 반복성은 확인하지 않았다(추가 측정은 하지 않기로 결정). "1회 측정에서 관측"이라고 쓴다.
  - S0의 1회당은 호버 마커, T1의 1회당은 외곽선 갱신 마커 기준이다. 정확히 어느 코드가 얼마를 할당했는지는 분리하지 않았다.
  - 이 처리의 할당은 **프레임 전체 할당(약 40 MB)의 0\~6.5%**다. 나머지는 이 측정 밖의 할당이다.
- **쓰면 안 됨**: "GC를 없앴다"(T1 정지 상태 0 B는 이 구간·이 조건의 관측일 뿐), "GC 스파이크 제거", 프레임 전체 GC(40 MB대)를 점령 코드의 할당량처럼 인용하는 것.
- 근거: 09 §5, `summary/section_gc.md`.

### 2-6. 전체 프레임 시간 — 개선을 확인하지 못한 수치 (반드시 함께 밝힐 한계)

**한 줄**: 전체 프레임 시간은 S0·T1 모두 약 44\~46 ms이고, 런 간 변동과 구별되는 일관된 향상은 확인하지 못했다. 참고로 하이라이트 처리는 S0에서도 프레임 시간의 약 1.7\~1.8%였다.

| 시나리오 | S0 프레임 시간 중앙값 (런별 범위) | T1 프레임 시간 중앙값 (런별 범위) | T1 − S0 | 계산: S0에서 호버 처리가 차지한 비중 |
|---|---|---|---:|---:|
| A | 44.55 ms (43.77\~45.22) | 44.91 ms (44.12\~46.26) | +0.36 ms | 약 1.7% |
| B | 45.62 ms (44.24\~45.95) | 44.10 ms (43.55\~45.71) | −1.52 ms | 약 1.8% |
| C | 44.83 ms (43.05\~44.88) | 44.52 ms (43.98\~45.76) | −0.31 ms | 약 1.8% |
| D | 44.83 ms (40.25\~45.77) | 45.41 ms (44.81\~45.49) | +0.58 ms | 약 1.8% |

(T1 − S0는 표에 적은 반올림값끼리 뺀 값이다.)

(비중 = 2-2의 프레임당 평균 ÷ 프레임 시간 중앙값. 서로 다른 통계를 나눈 근사다.)

- **읽는 법**: T1−S0의 방향이 시나리오마다 섞여 있고(+0.36 · −1.52 · −0.31 · +0.58 ms) 두 변형의 런별 범위가 겹친다. 그래서 "전체 프레임 시간이 좋아졌다"고도, "좋아지지 않은 이유가 X다"라고도 확정하지 않는다.
  줄어든 처리 시간(프레임당 약 0.75\~0.8 ms)이 런 간 변동보다 작다는 것까지가 관측이다. 이 장비·에디터에서는 본 측정 A\~D의 모든 프레임이 16.7 ms를 넘었다(최소 `main_thread` 29.65 ms).
- **포트폴리오에서의 의미**: 이 결과는 "게임을 빠르게 했다"가 아니라 **"불필요하게 반복되던 작업을 찾아 없앴고, 그 구간의 비용을 수치로 확인했다"**는 근거다.
  이 한계를 먼저 밝히면 배율(2-2)이 과장으로 읽히지 않는다.
- **쓰면 안 됨**: "FPS 향상", "프레임 드랍 해결", "60fps 기준 X% 절감"(이 장비에서는 60fps 조건이 성립하지 않는다).
- 근거: 09 §4 표 각주 ², §9.

### 2-7. 상태가 바뀔 때의 단발 비용 (E 표본) — 남은 과제

**한 줄**: 원정 출발·모드 재진입의 이벤트 처리 구간은 각각 중앙값 52.3·38.1 ms였고, 그 안의 청크 재분류가 33.0·37.6 ms를 차지했다. 이 값은 프레임 전체가 아니라 해당 마커 구간의 시간이다.

| 이벤트 | 상위 구간 (중앙값, 범위) | 그중 청크 재분류 | 재분류 밖 |
|---|---|---|---|
| 원정 출발 (`ConquerUI`) | 52.3 ms (31.9\~57.1) | 33.0 ms | 18.3 ms |
| 점령 모드 재진입 (`ModeEnter`) | 38.1 ms (27.3\~56.2) | 37.6 ms | 0.47 ms |

(10세션 중앙값. "재분류 밖"은 세션마다 뺀 차의 중앙값.)

- **의미**: 매 프레임 비용(2-1\~2-4)은 줄였지만, 상태 변경 시 단발로 생기는 재분류 비용(중앙값 약 33\~38 ms)은 남아 있다. **다음 최적화 대상**으로 제시하기 좋다.
  짧게 인용할 때는 "청크 재분류 중앙값 약 33\~38 ms"로 쓰고, 이벤트 구간 값(38\~52 ms)과 섞지 않는다.
- **쓸 때 붙일 단서**: S0에는 이 기능이 없어 **비교 대상이 없다**(개선 수치가 아님). 단발 이벤트라 범위가 넓다(약 2배).
  "재분류 밖" 18.3 ms가 어느 함수 몫인지는 나누지 않았다. 재진입 값은 워밍업 중 한 번 켰다 끈 뒤의 **재진입** 비용이다.
- **쓰면 안 됨**: 이 값을 개선 결과처럼 쓰는 것, 18.3 ms를 특정 UI 함수의 비용으로 단정하는 것.
- 근거: 09 §6.

### 2-8. 측정을 믿을 수 있는 근거 (방법론 어필용)

**한 줄**: 의도한 입력이 실제로 들어갔는지, 두 계측 경로의 값이 맞는지를 프레임 단위로 대조해 측정 자체를 검증했다.

| 검증 | 결과 |

| 넣은 입력 ↔ 게임이 읽은 셀 | 유효 런 전부 100% 일치 (불일치 런 2개는 무효 처리 후 재측정) |

## 3. 포트폴리오 문장 예시

### 한 줄
> 점령 모드 하이라이트를 "매 프레임 재구성"에서 "청크가 바뀔 때만 재구성"으로 바꿨고, 과거 경로를 이식한 에디터 플레이모드 비교(1,800프레임 가상 입력)에서 재구성은 1,800회 → 0\~76회, 해당 처리 누적 시간은 기존의 약 1/19\~1/38로 줄었다.

### 세 줄 (이력서·자기소개서)
> - 커서가 멈춰 있어도 매 프레임 청크 전체를 다시 칠하던 하이라이트를, 가리키는 청크가 바뀔 때만 외곽선을 다시 그리도록 개선했다.
> - 과거 구현을 현재 프로젝트에 이식해 같은 맵·같은 1,800프레임 가상 입력으로 Unity 에디터 플레이모드에서 비교한 결과, 재구성은 1,800회 → 0\~76회, 해당 처리 누적 시간은 약 1.35\~1.45초 → 0.036\~0.073초(19\~38배, 시나리오별 3회 측정 중앙값의 비)로 줄었다.
> - 이 처리의 비중은 프레임 시간의 약 1.7\~1.8%였다. 전체 프레임 시간에서는 런 간 변동과 구별되는 일관된 향상을 확인하지 못했고, 상태 변경 시 단발로 생기는 청크 재분류(중앙값 약 33\~38 ms)를 다음 개선 대상으로 남겼다.

### 한 문단 (포트폴리오 본문)
> 점령 모드에서 커서 아래 청크를 강조하는 기능은 커서가 멈춰 있어도 매 프레임 청크의 모든 셀을 다시 칠하고 있었다. 이를 "가리키는 청크가 바뀔 때만 외곽선을 다시 그리는" 방식으로 바꿨다. 효과를 확인하려고 과거 구현 경로를 현재 프로젝트에 이식하고, 같은 맵·같은 세이브·같은 가상 입력을 두 구현에 재생해 Unity Profiler로 비교했다(에디터 플레이모드, 시나리오 4종 × 3회). 1,800프레임(60fps 기준 30초 분량)의 가상 입력에서 재구성은 1,800회에서 0\~76회로, 해당 처리 누적 시간은 약 1.35\~1.45초에서 0.036\~0.073초로 19\~38배 줄었고, 해당 구간의 메모리 할당 총량도 약 2.2\~2.8 MB에서 0\~0.6 MB로 줄었다(시나리오별 각 1런 관측). 다만 이 처리의 비중은 프레임 시간의 약 1.7\~1.8%였고, 전체 프레임 시간에서는 런 간 변동과 구별되는 일관된 향상을 확인하지 못했다. 또 원정 출발·모드 재진입의 이벤트 처리 구간(중앙값 52.3·38.1 ms) 안에서 청크 재분류가 33.0·37.6 ms를 차지하는 것을 확인해 다음 최적화 대상으로 정리했다. 측정은 입력 일치·두 계측 경로 대조로 검증하고, 결과 표를 스크립트로 재생성할 수 있게 남겼다.

### 면접에서 "왜 FPS는 안 올랐나?"를 받으면
> 줄인 비용이 프레임당 약 0.75 ms인데, 에디터에서 측정한 한 프레임이 약 45 ms라 비중이 2%가 안 됐고, 전체 프레임 시간은 런마다 그보다 크게 흔들려서 일관된 향상을 확인하지 못했습니다. 그래서 이 개선은 FPS가 아니라 "불필요하게 반복되던 작업을 없애고 그 구간 비용을 수치로 확인한 것"으로 설명합니다. 대신 상태 변경 시 단발로 생기는 재분류 비용을 다음 대상으로 찾아냈습니다.

## 4. 모든 수치에 공통으로 붙는 단서

- **비교 대상**: 과거 커밋을 그대로 실행한 것이 아니라, 과거 처리 경로를 현재 프로젝트에 **이식**한 것과 비교했다(호환 변경은 [`호환범위.md`](./호환범위.md)).
- **환경**: Unity 에디터 플레이모드 · MacBook Air(M1) · 고정 카메라. Windows 빌드·다른 장비·다른 카메라에서는 재지 않았다.
- **원인 분리**: T1은 "변경 가드"와 "외곽선 표시"가 함께 바뀐 결과다. 각각의 기여는 분리하지 않았다.
- **반복**: 횟수·시간은 3회 반복(4회 합산도 같은 결론), GC는 1회.

## 5. 쓰면 안 되는 표현 (이유)

| 표현 | 이유 |
|---|---|
| "FPS가 N배 / N% 향상" | 전체 프레임 시간에서 일관된 향상을 확인하지 못했다(2-6) |
| "2% 미만이라 FPS가 변하지 않았다" (인과 단정) | 비중은 근사이고, FPS 불변이나 그 원인을 검증하지 않았다(2-6) |
| "실제 30초 플레이 동안" | 30초는 가상 입력의 기준 시간이고, 측정 창은 1,800프레임이다(실제 경과는 약 77\~86초) |
| "재분류에 38\~52 ms" / "한 프레임에 38\~52 ms" | 38\~52 ms는 이벤트 처리 구간 값이다. 재분류는 33\~38 ms, 프레임 전체 시간은 따로다(2-7) |
| "게임이 38배 빨라졌다" | 배율은 하이라이트 처리 구간에 한정된다 |
| "37.6배 향상"만 단독 표기 | 커서 정지 시나리오의 최댓값이다. 범위(19\~38배)로 쓴다 |
| "GC를 제거 / GC 스파이크 해결" | 구간·조건 한정 관측, 1회 측정, 1회당 할당은 T1이 더 크다 |
| "출시 당시 게임과 비교" | 과거 경로를 현재 프로젝트에 이식한 비교다 |
| "가드 덕분에 N배" / "외곽선 덕분에 N배" | 두 변경의 기여를 분리하지 않았다 |
| "정지 시 비용 0 / 20 µs" | 계측 오버헤드가 섞인 관측값이다 |
| "Windows에서 / 실제 빌드에서" | 에디터 플레이모드에서만 쟀다 |
