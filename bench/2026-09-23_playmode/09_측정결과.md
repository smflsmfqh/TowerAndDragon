## 0. 한 문단 요약

과거 커밋은 에셋·데이터 구조가 달라 직접 실행하기 어려워, 당시 하이라이트 처리 경로를 현재 프로젝트에
이식(S0)하고 현재 실제 구현(T1)과 **같은 맵·같은 초기 상태·같은 입력**에서 비교했다.
1,800프레임 × 8칸 × 3회를 기본으로 측정했고, 관측된 누적 비용 차이의 주요 요인은 **재구성 횟수 감소**다. 재구성 1회 비용도 달라졌다.
S0는 커서가 멈춰 있어도 매 프레임 청크 전체를 다시 칠하고(1,800회), T1은 해석된 청크가 바뀔 때만 다시 그린다(0\~76회).

**이 수치는 에디터 플레이모드에서 해당 처리 구간을 잰 값이며 게임 전체 FPS를 뜻하지 않는다.**

단정할 수는 없다. 다른 줌·위치에서 같은 결과가 나오는지는 측정하지 않았다.

## 4. 본편 — S0 ↔ T1 (A\~D)

1,800프레임, 본 측정 3회 기준. 절대값을 먼저 읽는다.

| 변형 / 시나리오 | 실제 재구성 | 호버 누적 ms<br>중앙값 (최소\~최대) | 재구성 1회 µs<br>p50 / p95 ¹ | 프레임 시간<br>중앙값 ² |
|---|---:|---|---|---:|
| **S0 / A** | 1800 | 1348.6 (1204.4\~1463.2) | 651.1 / 1096.2 | 44.6 ms |
| **T1 / A** | 0 | 35.9 (35.0\~37.2) | — / — | 44.9 ms |
| **S0 / B** | 1800 | 1453.8 (1390.8\~1467.6) | 713.4 / 1144.7 | 45.6 ms |
| **T1 / B** | 11 | 48.7 (47.1\~50.2) | 334.1 / 582.0 | 44.1 ms |
| **S0 / C** | 1800 | 1446.1 (1390.4\~1467.2) | 705.8 / 1134.8 | 44.8 ms |
| **T1 / C** | 29 | 55.1 (54.8\~56.4) | 371.6 / 620.5 | 44.5 ms |
| **S0 / D** | 1800 | 1420.1 (1207.6\~1494.2) | 685.2 / 1150.4 | 44.8 ms |
| **T1 / D** | 76 | 73.3 (71.6\~74.2) | 360.1 / 585.1 | 45.4 ms |

¹ 런마다 재구성 마커가 발화한 프레임의 하네스 시간을 정렬해 0 기반 `floor(p·n)` 위치 값을 취하고, 그 값의 런 간 중앙값을 냈다(p50은 짝수 표본에서 가운데 두 값 중 윗값).
원본 생성 코드는 확인되지 않았고, 이 정의로 14개 값이 전부 재현된다(`--group main` 출력 「재구성 마커 시간 — (c)」).
현재 집계기 규칙(중앙값 `statistics.median`, p95 `round((n−1)·p)` 위치)으로 내면 T1/D p95는 **539.7 µs**(약 −7.8%)다 — 런당 발화가 76개뿐이라 p95가 분위수 규칙에 민감하다. 나머지 칸은 0\~0.8 µs 차이다(같은 출력의 (b) 열).
² 하네스 `main_thread_ns`의 런별 중앙값 → 런 간 중앙값. `unscaled_delta_ns`로 내면 43.81\~45.41 ms다.

### 실제 재구성 횟수 — 이 비교의 본질

| 시나리오 | S0 | T1 |
|---|---:|---:|
| A 정지 | 1,800 | **0** |
| B 5셀/기준초 | 1,800 | **11** |
| C 15셀/기준초 | 1,800 | **29** |
| D 40셀/기준초 | 1,800 | **76** |

**이 값은 세 반복에서 한 번도 흔들리지 않았다**(전 칸 최소=최대). 입력이 프레임 단위로 재현되기 때문이다.

### 배율은 뒤에 쓴다

호버 처리 누적 시간 기준: A **37.6배** · B **29.9배** · C **26.3배** · D **19.4배**.
보완 런을 합쳐 4회로 내면 36.2 / 29.2 / 25.5 / 19.8배로 **결론이 바뀌지 않는다.**

**입력이 빠를수록 배율이 줄어든다** — T1의 재구성 횟수가 늘기 때문이고, S0는 원래 항상 최대 작업을 한다.

> **재생성 명령** (저장소 루트, 런 그룹은 `runs_manifest.json`이 정한다)
>
> ```bash
> python3 bench/summarize.py bench/2026-09-23_playmode --group main          # 본 측정 44런 → §4 표·§6 표
> python3 bench/summarize.py bench/2026-09-23_playmode --group all           # 54런 → 4회 합산 배율
> python3 bench/summarize.py bench/2026-09-23_playmode --group supplemental  # 보완 10런 → §5 구간 GC
> ```
>
> 출력은 `summary/summarize_output_{main,all,supplemental}.md`에 있다. 각 표 위에 입력 그룹·계산법·측정 창이 적혀 있다.
> `summary/summarize_output.md`는 M8 당시 집계기의 출력(본 측정·보완을 풀링한 4회 기준)이며 기록으로 남겨 두었다 — 이 표와 대조하지 않는다.

재구성 1회당 비용은 T1이 334\~372 µs, S0가 651\~713 µs로 T1이 절반 수준이지만,
**차이의 대부분은 호출 횟수에서 온다.**

배율을 내지 않은 것: 재구성 횟수(T1/A가 0이라 분모가 0), T1의 재구성 미발생 프레임 비용(19\~22 µs로, 오버헤드 기여를 분리하지 못한 관측값),
E 표본(단발 1회라 산포가 약 2배), 하네스·명시적 마커 오버헤드(별도 비용을 분리 추정하지 못함).
19\~22 µs 자체가 계측 해상도 이하라고 확인한 것은 아니다.

### 재구성 발생 프레임과 미발생 프레임을 나누면

전체 p95는 재구성 미발생 프레임이 다수일 때 재구성 발생 프레임의 비용을 숨긴다.
아래는 재구성 마커 발화 여부로 나눈 **호버 구간 시간**이며, 커서 이동·청크 전환 여부로 나눈 통계가 아니다.
단위 µs, 본 측정 유효 3런의 프레임을 합쳐(풀링) 계산했다.

| 시나리오 | S0 재구성 발생 p50 ⁴ | T1 재구성 발생 p50 ⁴ | T1 재구성 발생 프레임 수 | T1 재구성 미발생 p50 ⁴ |
|---|---:|---:|---:|---:|
| A | 686.5 | — | 0 | 19.1 |
| B | 752.8 | 371.9 | 33 | 21.7 |
| C | 746.2 | 401.5 | 87 | 21.5 |
| D | 705.2 | 386.5 | 228 | 21.6 |

⁴ 풀링한 하네스 `*_hover_ns`를 정렬해 0 기반 `round((n−1)·0.5)` 위치 값(짝수 표본에서 가운데 두 값 중 하나라 "중앙값" 대신 p50으로 적는다).
원본 생성 코드는 확인되지 않았고, 이 정의로 `transition_vs_still.md`의 22개 값이 전부 재현된다(`--group main` 출력 「재구성 발생/미발생 분할」의 `⟨ ⟩` 값).
현재 집계기의 중앙값(`statistics.median`, 짝수면 두 값의 평균)으로는 S0/B 752.7, T1/D 386.2이고 나머지 칸은 같다.

**S0는 커서가 정지해도 매 프레임 재구성한다.** 따라서 S0의 재구성 미발생 표본은 없지만,
입력이 정지한 표본은 있다(A 시나리오). 이 표의 S0 전체 프레임과 T1 재구성 발생 프레임은
서로 같은 입력 전환 조건으로 묶인 표본이 아니므로, 순수한 청크 전환 1회 비용 비교로 해석하지 않는다. 자세한 표는 [`summary/transition_vs_still.md`](./summary/transition_vs_still.md).

## 5. 구간별 GC — 전체 프레임 GC로 대신 말하지 않는다

보완 10런에서 `HierarchyFrameDataView`의 `columnGcMemory`로 뽑았다. **런당 1회이며 반복의 중앙값이 아니다.**
재생성: `--group supplemental` 출력 「구간 GC」(측정 창 합계, 중첩 마커는 시나리오별 고정표로 합계에서 제외).

| 런 | 구간 합계 | 전체 프레임 GC | 구간/전체 |
|---|---:|---:|---:|
| `S0_A_run4` | 2,188,800 B | 42,691,062 B | 5.13% |
| `S0_D_run4` | 2,792,760 B | 43,569,079 B | 6.41% |
| `T1_A_run4` | **0 B** | 40,284,480 B | 0.00% |
| `T1_D_run4` | 598,576 B | 40,889,651 B | 1.46% |

- **전체 프레임 GC는 40 MB대지만 구간 GC는 0\~2.8 MB다.** 나머지는 해당 마커 밖에서 관측한 할당이므로
  **전체 프레임 GC를 점령 코드의 할당량으로 인용하면 안 된다.**
- S0의 할당은 전부 `s0_hover`에 있고 `s0_rebuild`(그리기 루프)는 0이다. 할당은 `s0_hover` 안·`s0_rebuild` 밖에서 관측되며,
  그 범위에는 코드상 커서·청크 조회, 출발 가능 판정, `GetChunkCellCoords()`의 `new List<Vector3Int>` 생성·좌표 복사가 함께 있다.
  **개별 할당처의 비중은 분리하지 않았다.** 회당 1,216\~1,558 B.
- T1은 **재구성 마커(`t1_hoveredborderrebuild`) 구간에서 대부분(약 99.5%)이 관측된다.** 그 구간은 셀 `HashSet` 생성과
  폐곡선 목록 생성을 함께 포함하며, **둘의 비중은 이 측정으로 갈리지 않는다.**
- **회당으로는 T1이 더 많이 할당한다**(D에서 T1 7,876 B/회 ↔ S0 1,552 B/회). 총량이 적은 것은
  횟수(76 ↔ 1,800) 때문이다. 방향이 엇갈리므로 배율 하나로 뭉뚱그리지 않는다.

자세한 표는 [`summary/section_gc.md`](./summary/section_gc.md).

- (2026-10-02 정정 — 이전 문장 "전이는 30프레임째"는 E-출발의 발화 프레임(39)과 E-재진입의 준비·워밍업 조건을 구분하지 않았다.)

|---|---|---|
| 상위 구간 전체 | `ConquerUI` **52.3 ms** (31.9\~57.1) | `ModeEnter` **38.1 ms** (27.3\~56.2) |
| 그 안의 재분류 | `Reclassify` **33.0 ms** (21.0\~35.1) | `Reclassify` **37.6 ms** (27.0\~55.5) |
| 상위 − 내부 (세션별 차의 중앙값) | **18.3 ms** | **0.47 ms** |

- 두 경우 모두 **비용의 본체는 청크 재분류**다.
- 상위 − 내부는 **상위 마커 안·재분류 마커 밖에서 관측된 시간**이다. 세션마다 차를 구한 뒤 중앙값을 냈다(두 중앙값의 차가 아니다).
- E-재진입은 이 잔여가 0.47 ms라, 이 조건에서 **`ModeEnter` 구간 시간의 대부분이 재분류 구간에서 관측됐다.**
  잔여 구간에는 코드상 사운드·건설 취소·테두리 정리 호출이 있지만, 마커가 그 안을 나누지 않아 개별 함수의 기여는 확정하지 않는다.
- E-출발의 잔여 18.3 ms도 같은 성격이다. 그 구간에는 코드상 자원 차감·슬롯 갱신·크루 연출·`Close()` 호출이 있지만, **어느 함수가 얼마인지는 이 측정으로 갈리지 않는다.**
  재분류 마커를 따로 잡았으므로 이 잔여를 하이라이트 갱신(재분류) 비용으로 세지 않는다는 데까지만 말한다.
- **산포가 약 2배로 넓다.** 1,800프레임을 누적하는 A\~D와 달리 단발 이벤트 1회이며, 산포의 원인을 GC 타이밍으로 특정하지는 못했다.
  중앙값과 범위를 함께 읽어야 하고 **이 값으로 배율을 만들지 않았다.**

**S0는 N/A다.** 과거 경로에는 점령 모드 자체가 없고 상태 변경 시 갱신하는 구조도 없다.
지원하지 않는 기능을 no-op과 비교하지 않는다.

**상태 전이 검증 (E-재진입의 측정 밖 준비 단계)** — 본 측정 10세션과 보완 1세션 전부 원정 강제 완료 전후 `visible 12→14 · conquered 5→6 · conquerable 11→13 · 활성 원정 1→0` (`summary/T1_EReenter_run*.json`의 `territory_before/after`).
측정 창 안의 변화가 아니라, 재진입을 재기 전에 영토가 의도대로 바뀌었는지 확인한 기록이다. E-출발 런에는 이 기록이 없다.

**완료 상태 준비의 타당성** — M5는 완료 상태를 `DebugForceCompleteAllExpeditions()`로 만들었다.
같은 스냅샷에 대해 정상 정산(`OnNightEnd` → `OnSettlement`) 경로를 별도 세션에서 돌려 상태를 `diff`한 결과
**점령 관련 상태가 완전히 일치**했다([`summary/settlement_equivalence.md`](./summary/settlement_equivalence.md)).
단, 밤 전투를 치르지 않았으므로 자원·인구·일차는 다르다 — **점령 관련 상태에 한정한 검증**이다.

### 프레임별 대응의 판정 기준 — 사전 기준이 아니다

두 출처는 읽는 경로가 달라(하네스 `ProfilerRecorder.LastValue` ↔ raw 저장 샘플)
**양의 차이가 주로 관측됐다** — 하네스가 거의 항상 조금 크고(양수 99.58%, 음수 0.00%) 절대차 중앙값은 125 ns다
(54런 91,057쌍, `--group all` 출력 「프레임 대응 요약」. 2026-10-01 정정 — 이전 문장의 126 ns는 이 집합의 값이 아니었고, 보완 10런만 모으면 126 ns다).
차이가 항상 일정하거나 원인이 특정됐다는 뜻은 아니다. 값이 작은 프레임에서는 이 차이가 상대 오차를 부풀린다.

그래서 **상대 ≤5% 또는 절대 ≤5,000 ns**를 판정선으로 썼고 91,057쌍 중 초과 1건이다.
⚠️ **이 절대값은 같은 자료의 차이 분포를 보고 정한 탐색적 기준이며, 측정 전에 정해 둔 사전 기준이 아니다.**
§2-4가 요구한 사전 정의 절대 오차를 파일럿에서 두지 못했고 그 공백을 사후에 메운 것이므로,
이 선을 통과했다는 사실만으로 정확도를 주장하지 않는다.
**대응의 1차 근거는 발화 프레임 일치(0건 불일치)와 오프셋 판정이다.**

초과 1건: `T1_D_run1` frameIndex 31, 하네스 73,375 ns ↔ raw 56,250 ns. **원인을 규명하지 못했고**
그 런의 `.raw`는 이미 지워 더 파고들 수 없다. 자세한 것은 [`summary/frame_alignment.md`](./summary/frame_alignment.md).

### 계측 한계로 남긴 것

- **명시적 마커 오버헤드** — 패치 있음 42.48 ms vs 없음 54.18 ms로 **패치 쪽이 더 빨랐다**.
  마커 구간 자체는 프레임당 약 19 µs인데 런 간 프레임 시간 변동이 ±12 ms라 3자리 크다. 분리 측정 불가.
- **하네스 오버헤드** — 같은 이유로 분리 측정 불가. 프레임 GC 합계는 사실상 동일.
- **엔진 자동 샘플** — `ConquestModeController.Update()`는 리코더에서 invalid일 뿐 아니라
  **이번 raw에서도 샘플을 찾지 못했다.** Deep Profile을 켠 별도 검증은 수행하지 않았다. 교차 확인은 raw 추출로 대체했다.
- ⚠️ **`ProfilerRecorder.Valid`는 "수집됐다"의 근거가 아니다.** 계측 패치를 제거한 런에서도
  8개 마커 전부 `Valid=true`였고 발화는 0이었다. 판별은 발화 프레임 수와 raw 호출 수로 한다.
