## 0. 목적과 범위

### 0-1. 질문

**실제 과거 구현을 현재 맵에서 실행했을 때와 실제 개선 후 구현의 처리 시간·관리 할당·갱신 횟수·렌더링 제출량이 어떻게 다른가?**

본편은 `038b253e`의 과거 하이라이트 경로(S0)를 현재 프로젝트에 충실하게 이식하고,
기준 커밋 `061cc138`의 실제 구현(T1)과 비교한다. 과거 커밋은 에셋·데이터 구조 변경으로
직접 실행하기 어려우므로 같은 현재 씬에서 비교한다. 이는 **동일한 현재 맵 조건에서의 구현 전후 비교**이며,
당시 게임 전체의 성능 재현은 아니다. 표시 범위·판정·캐시·표시 방식이 함께 바뀐 전체 효과를 측정한다.

가드와 표시 방식의 기여를 각각 분리하는 것은 본편 목표가 아니다. S1·T0 같은 실험용 변형은
필요할 때만 별도 보조 실험으로 추가하며 역사적 개선 전 구현으로 부르지 않는다.

### 0-2. 기존 결과를 대표 수치로 사용하지 않는 이유

| 문제 | 설명 |
|---|---|
| 원본 경로 누락 | 출시본의 셀 집합 할당·대상 판정·좌표 변환·인셋 등을 축약해 실제 구현 비용과 다르다 |
| 과거 하위 함수 불일치 | 현재 `HighlightCells`를 사용하면 과거에 없던 작업이 추가된다 |
| 렌더링 제외 | EditMode 측정은 실제 화면 렌더링·배칭 비용을 포함하지 않는다 |
| GC 계측 | 관리 힙 크기 차이는 정확한 누적 할당량이 아니다. 무할당 하드코딩은 최신본에서 일부만 수정됐다 |
| 누적값 불일치 | 고정 바이트 수로 누적 가비지를 계산해 해당 실행의 실측값과 연결되지 않는다 |

두 변화의 기여가 분리되지 않는 것 자체는 전체 개선 효과를 비교할 때의 결함이 아니다.
기존 자료는 삭제하지 않고 참고용으로 보존하며 새 측정 결과와 섞지 않는다.

### 0-3. 원칙과 범위

- 같은 `SampleScene`·현재 맵·초기 게임 상태·카메라·입력 시퀀스에서 S0와 T1을 비교한다.
- 과거 처리 경로는 보존하고, 현재 데이터에 연결하기 위한 호환 수정은 원본 diff와 이유를 남긴다.
- 개선 후는 복제 알고리즘 대신 실제 게임 메서드·컴포넌트를 실행한다.
- 본편은 실제 Unity Profiler를 사용하는 **에디터 플레이모드 조건의 비교**다. Windows Player 성과로 일반화하지 않는다.
- 옛 커밋 직접 실행은 시간 제한 탐색과 부록으로 둔다. 측정 코드·결과 작성은 후속 작업이다.

### 1-3. 과거 경로 이식의 충실도

- 상위 `HighlightHoveredChunk()`뿐 아니라 당시 `GetChunkCellCoords()`, `HighlightCells()`,
  풀 활성화·해제, 좌표 변환까지 호출 경로를 대조한다. 같은 이름의 현재 API가 동작까지 같다고 가정하지 않는다.
- 현재 `HighlightCells()`의 `EnsureRuntimeState`, 맥동 목록 정리, `RestoreDefaultSprite`,
  `GetCellSurfaceWorld()`를 그대로 호출하지 않는다. 과거는 `ConvertGridToWorld()`와 y 오프셋을 사용했다.
- 원본의 반복·할당·판정·엔진 호출을 보존한다. 현재 지형에 맞추기 위해 필요한 좌표·데이터 어댑터는
  별도 코드로 분리하고 비용 포함 여부와 변경 이유를 기록한다. 차이의 영향 방향을 모르면 모른다고 적는다.
- 현재의 `CanSendExpedition` 등 공유 의존성도 당시 구현과 비교한다. 현재 구현을 공통 사용해야 한다면
  그 범위를 명시하고, 전체 과거 경로를 완전히 복원했다는 주장을 피한다.
- T1은 실제 경로를 실행한다. HashSet·폐곡선 목록 할당, 편입 대상 판정, 인셋·월드 좌표 변환을 생략하지 않는다.
- 두 구현이 동시에 표시되지 않도록 실행 전 컴포넌트·풀·오버레이 상태를 확인한다. 초기화 비용은 별도 기록한다.

#### S0 풀 초기화 결정

- 드라이버가 **독립된 풀과 seed 렌더러를 소유**한다. 현재 컨트롤러의 선택 풀은 공유하지 않는다.
- 초기화 때 한 번만 리플렉션으로 현재 `MouseSelectController._selectionHighlightRenderer` 참조를 읽는다.
  `_spriteRenderer`는 과거 필드명이며 현재는 `FormerlySerializedAs`로만 남아 있다.
  이 참조는 반드시 프리팹 에셋이라는 뜻이 아니라 씬의 템플릿/seed 인스턴스일 수 있다.
- 해당 렌더러의 표시 설정을 가진 독립 SpriteRenderer를 벤치 전용 루트 아래에 준비하고,
  이를 템플릿과 `seedInstance`에 동시에 전달해 **0번 슬롯 재사용을 재현**한다.
  현재 컨트롤러 자체나 그 스크립트를 통째로 복제하지 않는다.
- 부모는 현재 선택 풀의 부모를 빌리지 않고 벤치 전용 루트로 고정한다. 원본 컨트롤러 transform과
  부모 계층·변환의 차이를 기록하고, 월드 위치·스케일·정렬·머티리얼·스프라이트가 의도대로인지 확인한다.
- 원본 seed를 공유하지 않는 차이는 격리를 위한 호환 변경이다. 실제 현재 에셋의 출처·GUID·표시 설정을
  기록하며 과거 렌더링 에셋까지 재현했다고 주장하지 않는다. 과거 풀 구현과 현재 구현의 동작 diff도 확인한다.
- 참조 획득·seed 생성은 초기화 측정에 포함하고 정상 상태 호버 측정 밖에서 수행한다.
  참조가 없거나 기본 하이라이트가 아닌 안내 스프라이트이면 파일럿을 실패 처리한다.

### 1-4. 선택적 원인 분석

S1(S0에 가드 추가), T0(T1의 호버 갱신 가드 우회)는 **실험용 변형**이며 본편에 필수가 아니다.
수행한다면 같은 계열 안에서 S0 ↔ S1, T0 ↔ T1만 가드 효과로 비교한다.
S1 ↔ T1, S0 ↔ T0는 표시 범위·판정·캐시가 달라 표시 방식만의 효과로 해석할 수 없다.
리플렉션으로 선택 상태를 덮어쓰는 방식은 기본 계획에서 제외한다. 추가 계측의 오버헤드는
파일럿에서 측정하고, `0.2 µs` 또는 `1% 미만`이라고 미리 단정하지 않는다.

## 2. 공통 측정 설계

### 2-1. 시나리오

워밍업을 마친 뒤 **별도 1,800프레임**을 측정한다. 이는 60fps 기준 30초 분량의 입력이며,
실제 경과시간도 별도 기록한다. 느린 런을 30초 실측이라고 부르지 않는다.

| ID | 내용 | 비교 범위 |
|---|---|---|
| A 정지 | 점령 가능한 Visible 청크 위에 커서 고정 | S0 ↔ T1 |
| B 5셀/기준초 | 미리 저장한 중앙 행 경로 왕복 | S0 ↔ T1 |
| C 15셀/기준초 | 같은 경로, 기준 60프레임당 15셀 진행 | S0 ↔ T1 |
| D 40셀/기준초 | 같은 경로, 기준 60프레임당 40셀 진행 | S0 ↔ T1 |
| E 상태 변경 | E-출발: 실제 UI 출발 시 갱신. E-재진입: 완료된 영토 상태에서 점령 모드 재진입 갱신 | T1의 이벤트 비용, 지원되는 과거 경로는 별도 비교 |

- 경로는 프레임 인덱스로 계산한다. 대상에서 제외되는 셀을 건너뛴다면 이동은 지형상 연속 이동이 아닌
  합성 입력임을 기록한다. 작은·큰 청크, 편입 영역을 포함하는 별도 검증 경로도 준비한다.
- 같은 저장된 초기 상태(청크 공개·점령·원정 상태, 자원·인구, 시드 등)에서 시작한다.
  배경 시스템의 진행 조건도 고정한다. 같은 씬만 여는 것으로 초기 상태가 같다고 가정하지 않는다.
- 워밍업은 최소 120프레임에 더해 측정 경로 전체와 최대 풀 용량을 경험하도록 한다.
  첫 진입·풀 확장 비용은 별도 초기화 측정으로 보존한다.
- E는 동일 상태에서 `RefreshConquerableHighlights()`만 반복 호출하지 않는다.
  변경 전후 상태·예상 표시를 저장하고 실제 전이를 검증한다. 독립 이벤트 샘플을 예를 들어 10회 수집하며,
  상태 복원은 측정 밖에서 수행한다. 지원하지 않는 과거 기능은 **N/A**로 쓰고 no-op과 비용을 비교하지 않는다.
- 상태 변경 없이 함수를 반복 호출하는 실험이 필요하면 “동일 상태 재분류 재호출”이라는 별도 항목으로 분리한다.

#### E 실행 경로와 표본 독립성 결정

- **실제 UI 경로를 사용한다.** 출발은 대상 선택과 정상 버튼 동작을 통해
  `UI_ConquestWindow.OnConquerButtonClicked()`의 `SendExpedition` → 자원 차감 →
  `RefreshConquerableHighlights` → 연출/Close 흐름을 실행한다. 매니저만 직접 호출해 대체하지 않는다.
- **E-재진입(완료 표본)은 완료된 영토 상태에서 `SetConquestModeActive(true)`로 실행되는 갱신**으로 정의한다.
  정상 밤 흐름에서는 점령 모드가 꺼지고 UI 구독이 해제되므로 완료 순간의 하이라이트 갱신을 전제로 하지 않는다.
  실제 모드 진입 전체와 내부 `RecomputeConquerableClassification` 구간을 나눠 기록한다.
- 완료 상태 준비에는 **측정 밖에서 `DebugForceCompleteAllExpeditions()`를 사용**한다.
  이 함수와 실제 정산은 공통 `CompleteConquest()`를 사용한다. 다만 디버그 함수는 모든 활성 원정을
  일수에 관계없이 완료하므로, 완료시킬 원정만 포함한 고정 스냅샷을 사용한다.
  모드와 패널은 닫힌 상태로 준비하고 완료 이벤트를 수동 Invoke하지 않는다.
- 디버그 경로가 게임 전체 정산과 동등하다고 주장하지 않는다. 완료 후 청크/공개/편입 상태,
  활성 원정, 자원·인구·연구 등 표시 판정 의존 상태와 풀·캐시 준비 조건이 같은지 검증한다.
  발생한 비동기 표시 작업이 끝나고 배경 상태가 안정된 뒤 기록을 시작한다.
  파일럿에서 정상 완료 경로의 상태와 비교해 이 전제를 확인하며, 불일치가 있으면 준비 절차를 수정한다.
  **상태와 준비 조건이 같을 때의 재진입 경로만 비교**하므로 본 측정에서 밤 웨이브를 10번 재생할 필요는 없다.
- E-출발과 E-재진입은 서로 다른 표본군이다. 유형별 동일한 스냅샷을 준비하고
  **각 샘플마다 새 플레이 세션에서 같은 상태를 복원**해 누적 영토 증가를 제거한다.
  유형별 10회 수집을 기본으로 한다. 세이브가 복원하지 않는 UI·캐시·난수 상태는 동일한 초기화 절차로 맞춘다.
- 복원·완료 상태 준비·워밍업은 측정 밖에서 처리한다. UI/모드 동작 전체와
  하이라이트 갱신 구간은 마커를 분리해 UI 생성·연출 비용을 하이라이트 비용으로 오인하지 않는다.
- 실제 정산 비용이 필요하면 **별도 선택 측정**으로 기존 `SETTLEMENT_MARKER`
  (`TND.Conquest.Settlement`)를 사용한다. 이 마커는 `OnSettlement` 내부의 원정 일수 진행·완료 처리 루프를
  감싸며, 루프 뒤 `OnExpeditionsChanged` 호출과 다른 시스템의 정산까지 포함한 전체 정산 비용은 아니다.
  디버그 완료 함수는 이 마커를 통과하지 않는다. 기존 마커는 이번에 추가한 임시 패치로 오인해 제거하지 않는다.

### 2-2. 기능·입력 정확성 관문

1. 측정 프레임의 의도 셀과 실제 읽은 셀 시퀀스가 일치한다. 프레임 대응 오류는 허용 비율로 넘기지 않는다.
2. 실제 해석된 점령 대상도 기록한다. 편입 청크가 같은 소유 대상에 연결되는 의미 차이는 예상 결과와 대조한다.
3. 좌표가 같아도 상태가 바뀌면 필요한 색·범위가 갱신된다.
4. 빈 영역 진입 시 이전 표시가 제거되고, 사용하지 않는 풀 객체가 남지 않는다.
5. 경계선은 구멍·분리 영역·대각선 접촉에서 올바르다. 대표 화면과 기대 결과를 남긴다.
6. S0·T1은 각 시점의 의도된 기능을 만족한다. 기능이 다른 부분은 누락 버그와 구분해 기록한다.

### 2-3. 지표와 집계 범위

| 지표 | 계측·해석 |
|---|---|
| 호버 처리 시간 | 양쪽 대응 구간을 동일한 범위의 명시적 `ProfilerMarker`로 계측. 선택·닫기 입력을 포함하는 T1 Update 전체와 S0 하이라이트만 직접 비교하지 않는다 |
| 경계·셀 재구성 시간 | 실제 작업 함수의 호출 수, 호출당 중앙값·p95·최대, 세션 누적 시간 |
| 갱신 횟수 | 입력 셀/청크 변경, 해석된 대상 변경, 실제 표시 재구성 호출을 각각 센다. 성과 표에는 실제 호출 수 사용 |
| 관리 할당 | 해당 구간의 GC Alloc과 전체 프레임 `GC Allocated In Frame`을 분리. 합계와 정지/전환/상태 변경별 값을 기록 |
| GC 작업 | GC 관련 마커 누적 시간과 관측 프레임 수. Incremental GC의 마커 발생 수를 완결된 수집 횟수로 부르지 않는다 |
| 전체 프레임 | 프레임 경과시간 분포와 16.7 ms 초과 프레임 수. `Main Thread − WaitForTargetFPS`는 다른 대기가 남을 수 있는 보조값이며 순수 CPU 실행시간으로 부르지 않는다 |
| 렌더링 제출량 | Batches·SetPass·Draw Calls. GPU 시간 개선의 증거로 단독 사용하지 않는다. 렌더링 시간 마커는 현재 URP에서 실제 발화되는 항목을 검증 후 사용 |
| 형상·규모 | 대상 셀 수, 경계 변 수, 폐곡선 수, 표시 대상 수. 셀당 비용만으로 다른 맵을 동등 정규화하지 않는다 |
| 이벤트 비용 | E의 실제 상태 전이·갱신 구간과 해당/후속 프레임 비용. 지연된 렌더링 작업도 확인 |

명시적 마커 Begin/End 비용이 짧은 가드 경로와 비슷할 수 있다. 과거 축약 측정의 약 0.1 µs를
현재 실제 경로의 예상값으로 확정하지 않는다. 엔진의 `ConquestModeController.Update()` 자동 샘플도
교차 확인용으로 기록하고, 파일럿에서 명시적 마커 유무를 비교한다. 자동 샘플 역시 무오버헤드 기준이 아니며
선택·닫기 입력을 포함하므로 호버 마커와 같은 값이라고 요구하지 않는다. 구분하기 어려운 정지 시간은
계측 한계를 명시하고 큰 배율 대신 실제 호출 수·할당·누적값을 우선 제시한다.

정지 프레임이 다수이면 전체 p95가 전환 비용을 숨길 수 있으므로 전환 호출 통계도 별도로 낸다.
호버 마커에 포함되지 않는 경계선 맥동·렌더링·후속 작업은 별도 항목으로 기록하고 중첩 시간을 중복 합산하지 않는다.

### 2-4. 반복·채택·유효성

- 먼저 S0·T1 파일럿으로 기능·마커·입력·할당을 확인한다. 파일럿 결과는 본 측정에서 제외한다.
- 본 측정은 S0·T1 × A~D × 각 3회로 시작한다. 순서를 교대하고 실행 순서·시각을 기록한다.
  E는 별도 이벤트 샘플을 수집한다. S1′는 선택적 추가다. 편차가 크면 원인을 점검하고 반복을 늘린다.
- 모든 런을 보존한다. 실행별 지표의 중앙값·최소/최대와 비교 배율의 계산 방식을 제시한다.
  지표마다 유리하거나 불리한 런을 골라 조합하지 않는다. 3회 결과의 꼬리 지연·최대값은 탐색적 수치로 취급한다.
- 각 변형·시나리오·런마다 플레이모드 재진입 및 초기 상태 복원을 수행한다.
- 무효 조건: 입력/상태 불일치, 예외, 누락된 프로파일 프레임, 마커 미수집, 프레임 대응 오류.
  **60fps 미달은 폐기 사유가 아니다.** 성능 저하는 결과로 남긴다.
- 가상 마우스 활성, 카메라 위치·회전·줌의 측정 중 불변을 확인한다.
- CSV와 raw는 같은 완료 프레임·스레드·단위·합산 범위로 대조한다. 목표 허용 오차는 ±5%이며,
  작은 값에는 사전 정의한 절대 오차도 사용한다. 차이를 수치 선별로 해결하지 않는다.

### 2-5. 환경·하네스 오버헤드

- Game 뷰 1920×1080·포커스, Scene 뷰 비활성, Deep Profile OFF, Profile Editor OFF,
  `targetFrameRate = 60`, `vSyncCount = 0`을 고정하고 실제 설정을 결과에 저장한다.
- 시간 측정과 상세 GC 할당 호출 스택 분석은 별도 실행으로 구분한다.
- 프레임별 데이터는 미리 할당한 숫자/구조체 버퍼에 보관한다. 문자열·CSV·JSON 생성, 파일 쓰기,
  로그 출력은 측정 후 수행한다. 입력 주입·리코더·검증 비용도 확인한다.
- 장비·OS·Unity 버전·기준 커밋·데이터/씬 해시·프로파일러 설정·GC 모드·실제 경과시간을 저장한다.
- 캡처와 raw 추출 전에 **Profiler Frame Count를 2,000으로 설정**한다. 측정 1,800프레임과
  시작/종료 여유 프레임이 들어가도록 하며, `ProfilerDriver.LoadProfile` 이후 실제 로드된 프레임 번호와
  개수를 하네스 메타데이터에 대조한다. 설정만으로 전체 로드를 보장하지 않는다. 기본 300 설정으로
  일부만 추출되는 상황을 막고, 보유 한도를 넘는 기록은 파일/구간을 분리해 누락 없이 검증한다.
- Profiler UI의 보유 프레임 수와 binary log 저장을 구분한다. 워밍업 뒤 파일 기록을 시작하고,
  프레임 누락 경고와 실제 raw 프레임 수를 확인한다. UI 버퍼 때문에 측정 길이를 단정하지 않는다.

### 3-1. 파일과 재현 자료

  Editor/BenchLauncher.cs                    ← 시나리오·런 지정, 씬/상태 초기화

과거 경로 원본·출처 커밋·호환 수정 이유와 실행 방법을 함께 보관한다.
`Assets/Bench` 실행용 사본을 정리하더라도 `source/`와 실제 코드 계측 패치는 삭제하지 않는다.
측정 소스를 보존하지 않은 결과만으로 재현 가능하다고 부르지 않는다.
실제 `Assets/Scripts`에 넣은 **계측 전용 패치는 측정 종료 후 작업 트리에서 제거하고 patches/의 diff만 보존**한다.
계측 전용 실제 코드 변경은 커밋하지 않는다. 적용 전 파일/사용자 diff를 저장하고 자신이 추가한 부분만
역적용한 뒤 원상 복원을 검증한다. 파일 전체 checkout/reset으로 기존 사용자 변경을 덮어쓰지 않는다.

기존 `06_`, `07_`, XML, raw, 벤치마크 소스는 참고용으로 그대로 보존하고 새 결과와 구분한다.
아카이브 이동은 이번 측정의 필수 단계가 아니다. 과거 결과나 커밋된 테스트를 임의로 삭제하지 않는다.

### 3-2. 실행 순서

1. 기준 커밋·현재 작업 변경·맵/씬/설정 해시를 기록한다. 실제 코드에 필요한 계측 변경은 별도 패치로 남긴다.
2. `SampleScene` 초기화와 GridMap 준비를 기다린다. 부트스트랩이 필요하면 정상 진입 흐름을 사용한다.
3. 저장된 초기 게임 상태를 복원하고 카메라·해상도·시간 설정을 적용한다.
4. 가상 마우스 입력을 준비한다. 다음 프레임 입력 큐와 실제 처리 순서는 파일럿에서 검증한다.
   입력 프레임 번호와 프로파일러 완료 프레임 번호를 각각 기록해 한 프레임 어긋남을 방지한다.
5. S0는 과거 드라이버, T1은 실제 점령 모드를 활성화한다. 다른 변형의 표시·업데이트가 남지 않는지 확인한다.
6. 경로 전체를 워밍업하고 초기 진입/풀 확장 정보를 별도 저장한다. 측정 시작 상태를 맞춘다.
7. raw 기록과 리코더를 시작하고 유효 마커·단위·스레드를 확인한다. 발생하지 않은 이벤트를 0으로
   기록할 때는 실제 미발생과 리코더 미지원/미수집을 구분한다.
8. A~D는 1,800프레임 동안 숫자 버퍼에 기록한다. E는 실제 상태 변경 전후와 정상 갱신을 기록한다.
9. 마지막 측정 프레임의 완료 샘플까지 읽고 기록을 종료한다. raw 파일을 닫고 프레임 누락을 확인한 뒤
   CSV·JSON을 생성한다. `Profiler.logFile` 등 설정과 입력 장치를 정상/예외 종료 모두 복원한다.
10. 다음 변형·시나리오·런은 새 플레이 세션과 동일 초기 상태에서 시작한다.

### 3-3. Unity 작업과 추출

Unity 씬·컴파일·플레이 작업은 프로젝트 규칙에 따라 Coplay MCP로 수행한다.
사용 가능한 도구와 프로젝트 연결을 먼저 확인하며, 특정 도구의 존재나 반환값을 가정하지 않는다.
Coplay의 상위 비용 프레임 요약은 원자료를 탐색하는 보조 자료이며 독립적인 절대값 보증으로 부르지 않는다.

raw 추출기는 프레임별 마커 시간·호출·GC Alloc을 같은 스레드와 범위로 읽는다.
동일 이름의 여러 샘플 및 중첩 포함시간을 중복 합산하지 않도록 파일럿에서 확인한다.
사용 중 Unity 버전의 API·마커 지원 여부를 검증하고, 하네스와 raw 집계가 일치하지 않으면
프레임 번호·단위·포함시간·스레드부터 점검한다.

### 3-4. 결과 표

| 변형 / 시나리오 | 실제 재구성 횟수 | 호버 처리 누적 ms | 전환 호출 중앙값 / p95 | 구간 GC 합계 | 전체 프레임 GC 합계 | GC 작업 관측 프레임 / ms | Batches / SetPass |
|---|---:|---:|---:|---:|---:|---:|---:|

- 본편 표: S0 ↔ T1, 같은 조건에서 각 런 값과 실행 간 중앙값·범위.
- 보조 표: S1′ ↔ T1, 표시 범위·의존성 차이 명시.
- E 표: 실제 상태 전이, 구현별 지원 여부, 이벤트 구간 시간·할당·후속 프레임 비용.
- 절대 시간·호출 수·할당량을 먼저 쓰고 배율을 뒤에 쓴다. 0 또는 계측 해상도 이하 값에는 무한대 배율을 붙이지 않는다.
- 정지·전환·초기화·상태 변경을 분리한다. 전체 게임 FPS 개선이나 GC 스파이크 해결은 해당 증거가 없으면 주장하지 않는다.

## 4. 부록 — 과거 커밋 직접 실행 탐색

쌍당 최대 2시간의 선택 작업이다. 현재 작업 트리를 전환하지 않고 별도 worktree를 사용한다.
옛 맵·씬의 결과는 본편과 별도 표로 둔다.

| 우선순위 | 커밋 쌍 | 확인할 내용 |
|---|---|---|
| 1 | `4cb924c5` ↔ `c698a4db` | 전체 후보 스프라이트 표시에서 틴트·경계 표시로 바뀐 실제 이력. 씬·프리팹·데이터 등 동반 변경을 먼저 조사 |
| 2 | `038b253e` ↔ `cb76a16f` | 가드 도입과 표시 범위 확대가 함께 일어난 이력. 가드만의 효과로 해석 금지 |

1. 해당 커밋의 Unity 버전, Imported 경로·메타·실제 의존 커밋을 확인한다. 날짜만으로 에셋 버전을 확정하지 않는다.
2. 별도 worktree에서 의존성을 준비하고 Coplay 연결로 컴파일 → 씬 → 플레이 → 표시 정상 여부를 확인한다.
3. 관문에서 막히면 오류·시도·시간을 기록하고 종료한다. 성능 측정을 위해 과거 기능을 임의로 제거하지 않는다.
4. 실행되면 동일 입력 재생·계측을 이식하고 지원되는 시나리오를 측정한다.
5. 다른 맵임을 명시하고 셀·경계 변·루프·표시 수를 함께 기록한다. 셀당 단가로 본편과 동등하게 환산하지 않는다.
6. 소스·호환 패치·원자료 보존을 확인한 뒤 만든 임시 작업 공간만 정리한다.

## 5. 결과로 주장할 수 있는 범위

| 주장 가능 | 현재 계획만으로 주장 불가 |
|---|---|
| 같은 현재 맵·초기 상태·입력에서 과거 이식 경로와 현재 실제 경로의 비용 차이 | 과거 출시 당시 게임 전체의 정확한 비용 |
| 실제 재구성 호출 수, 해당 구간 시간·관리 할당량의 차이 | 가드와 표시 방식 각각의 독립적 기여율 |
| 실제 상태 전이에 따른 갱신 비용과 표시 정확성 | 동일 상태에서 갱신 함수만 호출한 결과를 영토 변화 비용으로 표현 |
| 에디터 플레이모드 조건에서의 렌더링 제출량과 프레임 지표 | Windows Player·GPU 성능·FPS 향상으로 일반화 |
| 측정 구간에서 관측한 할당·GC 작업 | 모든 상황에서 무할당 또는 GC 스파이크 완전 제거 |

에디터 수치는 그 환경의 측정값으로 제시할 수 있다. 에디터라는 이유만으로 상대 배율의
빌드 재현성이 보장되는 것은 아니다. Windows 성능을 대표 성과로 제시할 때는 같은 하네스를
Windows Player에서 다시 실행하고 빌드 백엔드·장비·설정을 명시한다. 이는 후속 단계다.

권장 설명:

> 과거 커밋은 에셋·데이터 구조 변경으로 직접 실행하기 어려워 당시 하이라이트 경로를 현재 프로젝트에
> 이식했다. 호환 변경을 기록하고 동일한 맵과 입력에서 현재 실제 구현과 비교했다.
> 이 수치는 에디터 플레이모드의 해당 처리 구간 결과이며 게임 전체 FPS를 뜻하지 않는다.

## 7. 실행 순서와 완료 조건

1. 과거 호출 경로·현재 공유 의존성 diff와 호환 범위를 확정한다.
2. 하네스·마커·추출기를 만들고 S0·T1 파일럿으로 기능·입력·프레임 대응을 검증한다.
3. S0·T1의 A~D 반복 측정과 E 이벤트 측정을 수행한다. 고정 75런 계획은 사용하지 않는다.
4. 편차와 알려진 공백을 검토한 뒤 필요한 반복·S1′·과거 worktree 부록을 추가한다.
5. 모든 실행 결과·소스·패치·설정·원자료와 한계를 결과 문서에 보존한다.
6. 재현 소스·패치 보존 확인 후 계측 전용 실제 코드 변경을 제거하고 적용 전 상태와 대조한다. 실행용 사본도 정리하되 측정 전부터 존재한 사용자 변경을 되돌리지 않는다.

소요 시간은 파일럿 후 산정한다. A~D 기본 24런, E-출발·E-재진입 각 10세션의
실제 진입·복원·워밍업·측정·저장 시간을 기록해 합산하고, 추출·검증·재실행 시간을 별도로 더한다.
E 상태 준비가 병목인지 우선 확인한다. 하네스 작성과 선택적 정상 정산 확인/worktree 탐색 시간은
반복 측정 시간과 분리해 예상치를 기록하며, 측정 전 고정 75런 또는 80분으로 약속하지 않는다.

완료 기준은 큰 배율을 얻는 것이 아니라 **원본 충실도·기능 정확성·동일 조건·계측 대응·재현 자료가 확인된 비교**다.

## 8. 계측 참고

- `GC.GetTotalMemory()` 차이는 수집이 관측되지 않고 다른 할당의 영향이 통제된 구간에서
  관리 힙 증가의 **거친 보조 추정치**로 사용할 수 있다. 특정 함수의 정확한 누적 할당량을 보장하지는 않으며,
  0이라는 값도 무할당 증명이 아니다. 런타임의 집계 특성·동시 할당 등 오차를 명시한다.
  본편은 프로파일러 할당 지표를 우선하고 과거 `MeasureAllocPerCall`을 동등한 대체 계측으로 쓰지 않는다.
- `GetAllocatedBytesForCurrentThread()`가 0을 반환했던 과거 환경 관찰은 모든 Mono의 일반 성질로 단정하지 않는다.
- Incremental GC는 여러 프레임에 나뉠 수 있다: [Unity Profiler 마커 설명](https://docs.unity.com/en-us/engine/6000.7/manual/analysis/profiler/markers).
- binary log는 UI 프레임 보유와 구분하며 누락 경고·종료 시 파일 닫기를 확인한다:
  [Unity binary log API](https://docs.unity.com/en-us/engine/6000.7/script-reference/unityengine/profiling/profiler/enablebinarylog).
- 참고 문서와 설치 Unity 버전이 다를 수 있으므로 실제 마커·API 지원은 파일럿에서 검증한다.
