## 2. 코드로 본 차이

### 2-1. 개선 전 — `038b253e`

```csharp
private void Update()
{
    if (!IsActive)
        return;

    HighlightHoveredChunk();   // ← 가드가 없다. 매 프레임 전부 다시 만든다.
    HandleSelectInput();
}

private void HighlightHoveredChunk()
{
    Vector3Int hoveredCell = _mouseSelectController.GetHoveredCell();
    Chunk chunk = _gridMap.GetChunkAt(hoveredCell);

    if (chunk == null) { _mouseSelectController.ClearHighlights(); return; }

    Color color = _conquestManager.CanSendExpedition(chunk.ChunkCoord)
        ? _conquerableHighlightColor : _blockedHighlightColor;

    _mouseSelectController.HighlightCells(GetChunkCellCoords(chunk), color);
}

private static List<Vector3Int> GetChunkCellCoords(Chunk chunk)
{
    var coords = new List<Vector3Int>(chunk.Cells.Count);   // ← 매 프레임 새 List
    foreach (GridCell cell in chunk.Cells) coords.Add(cell.Coord);
    return coords;
}
```

그리고 `MouseSelectController.HighlightCells`가 셀마다:

```csharp
SpriteRenderer highlight = pool.Get(i);          // gameObject.SetActive(true)
Vector3 cellPos = _gridMap.ConvertGridToWorld(coords[i]);
highlight.transform.position = cellPos;          // Transform 쓰기
highlight.color = color;                         // Renderer 쓰기
```

**이 구조가 프레임마다 하는 일** — 커서가 1픽셀도 안 움직여도 동일하게:
`List` 1개 새로 할당 → 청크의 셀 전부(중앙값 113칸) 순회 →
113 × (`SetActive` + 좌표 변환 + `transform.position` 쓰기 + `color` 쓰기).

### 2-2. 출시본 — 2단계로 나눈 갱신

```csharp
private void Update()
{
    if (!IsActive) return;
    HandleHover();          // ← 1단계: 싸다. 대부분의 프레임은 여기서 끝난다.
    HandleSelectInput();
    HandleCloseInput();
}

private void HandleHover()
{
    if (_isSelectionLocked) return;

    Vector3Int hoveredCell = _mouseSelectController.GetHoveredCell();
    Chunk chunk = _gridMap.GetChunkAt(hoveredCell);
    Vector2Int? hoveredChunkCoord = TryResolveConquestTarget(chunk, out var target)
        ? target : (Vector2Int?)null;

    if (hoveredChunkCoord == _selectedChunkCoord)
        return;                       // ★ 가드 — 커서가 같은 청크 위면 여기서 끝

    _selectedChunkCoord = hoveredChunkCoord;
    RefreshHoveredBorder();           // 호버 덩어리의 경계선만 다시 그린다
}
```

```csharp
// ★ 2단계: 비싸다. 영토가 실제로 바뀌었을 때만 호출된다 (호출 지점 3곳).
private void RecomputeConquerableClassification()
{
    foreach (Chunk chunk in _gridMap.GetAllChunks()) { /* 3분류 */ }

    CacheAnnexableNeighbors(...);     // 편입될 짜투리 미리 계산
    RefreshCandidateBorders();        // 후보 경계선
    RefreshTerrainTints();            // 지형 타일 색 (가장 비싼 단계)
    RefreshHoveredBorder();
}
```

**호출 지점 3곳** — 전부 "상태가 실제로 변한 순간"입니다.

| 지점 | 언제 |
|---|---|
| `SetConquestModeActive(true)` | 점령 모드에 들어갈 때 |
| `RefreshConquerableHighlights()` ← `UI_ConquestWindow:227` | 점령이 완료되어 영토가 늘었을 때 |
| `RefreshConquerableHighlights()` ← `UI_ConquestWindow:603` | 원정을 보내 청크가 "원정 중"으로 바뀔 때 |

### 2-3. 가드가 3겹이다

출시본은 같은 판단을 세 층에서 반복합니다 — 어느 한 겹이 뚫려도 다음 겹이 막습니다.

| 층 | 위치 | 조건 |
|---|---|---|
| 1 | `HandleHover()` | 호버 청크 좌표가 그대로면 반환 |
| 2 | `ShowHoveredBorder()` | 덩어리 집합이 `SetEquals`로 같고 **상태도** 같으면 반환 |
| 3 | `RefreshInProgressBorders()` / `ShowPreviewBorder()` | 대상 집합이 같으면 재구성 생략 |

2층이 상태까지 비교하는 이유가 코드 주석에 남아 있습니다 — *"원정을 보낸 직후처럼 좌표는
그대로인데 분류만 바뀌는 경우가 있어, 좌표만 비교하면 색이 갱신되지 않고 이전 색으로 남는다."*
**가드를 넣을 때 무엇을 놓칠 수 있는지까지 따진 흔적**입니다.

추가로 `FogOfWarRenderer`는 **프레임당 한 번으로 합치는** 장치를 따로 둡니다.
청크 하나가 열리면 셀 변경 이벤트가 수백 번 연달아 오는데, 셀마다 즉시 9×9 창을 다시 칠하면
같은 좌표를 수십 번 덧칠하게 됩니다. 그래서 좌표만 모아 두고 렌더링 직전에 한 번만 처리합니다
(`QueueRepaint` → `RepaintQueuedAsync`).

### 2-4. 할당 구조의 차이

| | 개선 전 | 출시본 |
|---|---|---|
| 좌표 리스트 | `new List<Vector3Int>(N)` **매 프레임** | 재사용 (`_hoveredChunkCoords`, `_claimGroupBuffer` 등 9개) |
| 경계 추적 | (없음) | `_borderEdges`, `_outgoingEdges`, `_isEdgeUsed` 전부 `readonly` 재사용 |
| 캐시 복사 | (없음) | `_lastHoveredChunkCoords.Clear(); UnionWith(...)` — 집합 재사용으로 할당 없이 복사 |

> 출시본 주석: *"인자는 호출자가 매번 Clear()해서 재사용하는 버퍼다 - 참조를 들고 있으면
> 다음 호버에 호출자가 지우면서 캐시가 조용히 오염되므로 내용을 복사한다(집합을 재사용해
> 할당은 없앤다)."*

## 3. 측정 결과

> **측정 방법**: 두 구현을 EditMode 벤치마크 한 파일에 나란히 이식해, **같은 맵 데이터**

> 경계 추적 알고리즘(`CollectBorderEdges` / `TraceLoops` / `FindNextEdge`)은 출시본
> `ConqueredChunkBorderRenderer`에서 그대로 옮겨 왔습니다.
>
> Unity 6000.3.15f1 · `-batchmode -nographics` · Apple Silicon · 워밍업 200회 후 2,000회 평균.
> **EditMode 배치모드 기준값**이므로 상대 비교에는 유효하지만, 절대값을 "빌드에서 이만큼 걸린다"로
> 옮기면 안 됩니다.
>
> 소스: `bench/ConquestHighlightBeforeAfterBenchmark.cs` · 원자료: `raw/ab_비교벤치마크.log`

### 3-0. 두 번 돌렸고, 보수적인 값을 쓴다

같은 벤치마크를 2회 실행했다. **실행 간 편차가 20% 정도** 있으므로 아래 표는 전부
**출시본에 불리한 쪽(= 개선 폭이 작게 나오는 쪽)** 값을 채택했다. 두 실행의 원자료는
`raw/ab_비교벤치마크.log`에 그대로 남겨 두었다.

1차와 2차 사이에 ④(60초 세션)의 **계측 방식을 고쳤다.** 1차는 프레임마다
`Stopwatch.Start()/Stop()`을 불렀는데, 그 오버헤드(수십 ns)가 출시본의 프레임당 비용(0.09 µs)과
같은 자릿수라 출시본 수치에 섞였다. 2차는 3,600프레임 루프 전체를 한 번만 감싼다.
**④는 2차 값만 쓴다.**

### 3-1. 한눈에 보기

| 지표 | 개선 전 `038b253e` | 출시본 `07596572` | 차이 |
|---|---:|---:|---:|
| 커서 정지 프레임 1개 | 69.19 µs | **0.09 µs** | **765배** |

| 프레임당 GC 가비지 | **약 1.9 KB** (약 115 KB/초) | **0 B** | 완전 제거 |
| 조기 반환 가드 | 0개 | 3겹 | — |
| 재사용 버퍼 | 0개 | 9개 | — |

**②가 뒤집히지 않은 점이 중요합니다.** 출시본은 "덜 자주 계산"할 뿐 아니라, **실제로 계산하는
프레임에서도 더 쌉니다.** 셀 113개에 스프라이트를 깔던 것을 폐곡선 경계선 하나로 바꾼 결과입니다
— 경계 변 수집과 루프 추적을 포함한 값인데도 더 빠릅니다.
(1차 실행에서는 75.55 → 47.24 µs로 1.6배였다. 편차가 크므로 **"1.2배 이상 빠르다" 정도로만 말한다.**)

### 3-2. 점령 모드 60초 체류 (3,600프레임) 누적

실제 맵 레이아웃 위를 지나가는 커서 궤적(가로 스윕 81칸)을 따라가며, 커서 속도별로 잽니다.
개선 전 루프와 출시본 루프를 각각 통째로 한 번씩만 계측했습니다.

| 커서 | 재계산 횟수 | 누적 CPU | 누적 가비지 |
|---|---:|---:|---:|
| **정지** | 3,600 → **1회** (3,600배↓) | 259.0 → **0.41 ms** (630배↓) | 약 6.5 MB → **0** |
| 초당 5칸 (천천히 훑기) | 3,600 → **34회** (106배↓) | 228.8 → **2.47 ms** (93배↓) | 약 6.5 MB → **0** |
| 초당 15칸 | 3,600 → **100회** (36배↓) | 231.8 → **6.45 ms** (36배↓) | 약 6.5 MB → **0** |
| **초당 40칸 (쉬지 않고 빠르게)** | 3,600 → **267회** (13배↓) | 233.8 → **16.67 ms** (14배↓) | 약 6.5 MB → **0** |

**가장 불리한 조건 — 커서를 60초 내내 초당 40칸으로 휘두르는 경우 — 에서도 14배**입니다.
플레이어가 실제로 하는 행동(지도를 보다 멈추고, 목표 청크로 옮기고, 다시 멈추는)에 가까울수록
격차는 90배 이상으로 벌어집니다.

가비지는 개선 전 프레임당 약 1.9 KB × 3,600프레임 ≈ **6.5 MB**이고, 출시본은 **정확히 0**입니다.
버퍼 9개를 전부 재사용하고 가드에서 조기 반환하므로 할당이 발생하지 않습니다.

### 3-3. 영토가 넓어질수록 (출시본의 "비싼 경로" 1회 비용)

출시본에서 전체 재계산은 **영토가 바뀔 때만** 돕니다. 그 1회가 얼마나 드는지, 판정 대상 청크가
늘어남에 따라:

| 판정 대상 청크 | 셀 | 1회 비용 | 매 프레임이었다면 |
|---:|---:|---:|---:|
| 1 | 75 | 0.012 ms | 0.1% |
| 4 | 304 | 0.048 ms | 0.3% |
| 8 | 639 | 0.109 ms | 0.7% |
| 16 | 1,433 | 0.253 ms | 1.5% |
| 24 | 2,327 | 0.433 ms | 2.6% |
| 32 | 3,306 | 0.626 ms | 3.8% |
| **41 (맵 전체 = 상한)** | **4,705** | **0.921 ms** | **5.5%** |

비용은 대상 청크 수에 거의 정비례합니다. **매 프레임 구조를 유지한 채 이 기능
(`4cb924c5`의 전체 청크 스캔 + 지형 틴트)을 얹었다면, 후반부에 프레임 예산의 5.5%를
아무 일도 없는 프레임에서까지 상시 지불했을 것입니다.** 실제로는 호출 지점이 3곳뿐이라
게임당 수십 회만 돕니다.

> **상한이라는 점을 밝힐 것**: 실제 판정 대상은 그 시점 `ChunkState.Visible`인 청크뿐입니다.
> 이미 점령한 청크(`Conquered`)와 안개 밖 청크(`Hidden`)는 루프에서 걸러지고, 틴트는
> `LandCellCoords`(육지 셀)만 대상이라 물·해안 셀은 빠집니다. 41개는 "모든 청크가 동시에
> 판정 대상일 때"의 상한입니다.

## 4. 이 개선을 어떻게 읽어야 하는가

### 4-1. 이 개선의 성격

**"느린 코드를 빠르게 만든 이야기"가 아닙니다.** 개선 전 코드도 1프레임에 69~72 µs —
프레임 예산의 약 0.42%로, 그것만으로는 눈에 띄는 프레임 저하를 만들지 않습니다.
실제로 만든 문제는 두 가지였습니다.

1. **아무 일도 없는 프레임에서 일한다.** 커서가 멈춰 있어도 초당 60회 같은 계산을 반복합니다.
   점령 모드에 1분 머무르면 3,600회 중 **3,599회가 버려지는 계산**입니다.
2. **초당 약 115KB의 가비지.** 조작을 하지 않아도 계속 쌓입니다. Mono GC 특성상 이는 프레임 저하가
   아니라 **주기적인 GC 스파이크**로 나타납니다 — 평균 FPS로는 잘 안 잡히고 1% low에서 드러납니다.

### 4-2. 진짜 값을 한 지점

`4cb924c5`에서 "점령 가능한 지역 전체를 한 번에 보여주기" 위해 판정 범위를
**호버 청크 1개(셀 113) → 전체 41개 청크(셀 4,705)로 최대 42배** 넓혔습니다.
같은 커밋에서 그 계산을 이벤트 3지점에 묶었기 때문에, **범위가 42배 커져도 호출 횟수는
늘지 않았습니다.**

만약 갱신 시점을 `Update`에 둔 채 범위만 넓혔다면 프레임당 예산의 5.5%를 상시
냈을 것이고(0.921 ms), 이 값은 **점령이 진행될수록 커집니다** — 자소서에 쓴 "후반부로 갈수록"이라는
감각이 정확히 이 곡선입니다.

### 4-3. 판단의 순서

| 흔한 접근 | 이 프로젝트에서 택한 것 |
|---|---|
| 렌더링 비용을 먼저 의심 (머티리얼·드로우 콜) | 먼저 **재보고**, 그리는 쪽이 아니라 **계산 시점**이 문제임을 확인 |
| 계산을 더 빠르게 (알고리즘 최적화) | **필요 없는 계산을 없앰** — 갱신 시점을 상태 변화로 한정 |
| 한 곳에 가드 추가 | **가드 3겹** + 프레임당 합치기 — 어느 하나가 뚫려도 다음이 막음 |
| 성능을 위해 기능을 줄임 | 오히려 **표시 범위를 42배 넓히면서** 비용은 낮춤 |

마지막 줄이 이 사례의 요점입니다. 갱신 시점을 먼저 좁혀 두었기 때문에, **나중에 기능을
키울 때 성능을 협상 조건으로 삼지 않아도 됐습니다.**

### 4-4. 이 측정으로 말할 수 있는 것 / 없는 것

| 말할 수 있다 | 말할 수 없다 |
|---|---|
| 두 구현의 1회 비용과 배수 | 실제 플레이 중 평균 FPS |
| 60초 세션의 누적 CPU·재계산 횟수·가비지 | "후반부에 몇 fps에서 몇 fps로 올랐다" |
| 대상 청크 수에 따른 비용 곡선 | 빌드(플레이 모드)에서의 절대값 |
| 프레임당 가비지가 0이 되었다는 사실 | GC 스파이크의 실제 빈도·길이 |

오른쪽을 채우려면 개선 전 코드로 되돌린 빌드를 만들어 후반부까지 직접 플레이해야 합니다.
**왼쪽만으로도 자소서·포트폴리오의 주장은 전부 뒷받침됩니다** — 오른쪽 표현("몇 fps → 몇 fps")은
쓰지 않습니다.
